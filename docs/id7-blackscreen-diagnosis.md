## 一、结论速览

黑屏不是一次故障，是**三层问题叠成的一个死循环**。按作用顺序：

| # | 问题 | 证据 | 后果 |
|---|---|---|---|
| **1** | 音频 SETUP 三档全被车机 **400 Bad Request** | 每次往返 ~2s，三次全败 → `全部候选档位协商失败` | 车机认为会话不完整，**发起 ctrl 邀请要求重建** |
| **2** | 正在推流时收到 ctrl 邀请 → **直接忽略** | `onCtrlInvite()` 首行 `if (... \|\| isStreaming()) return` | 车机等 **18 秒**后拆掉会话 → **黑屏** |
| **3** | 重连后**首帧是 P 帧而不是 IDR** | 8 次首帧 `NAL 类型=1`，全部在 **0.2 秒内**被车机断开 | 重连永远起不来 → **黑屏 → 再邀请 → 循环** |

一句话：**车机要求重建（问题 1→2）→ 我们拆了但不肯重建（忽略邀请）→ 车机强拆（黑屏）→ 我们重连却送不出 IDR（问题 3）→ 车机立刻再拒（黑屏）→ 车机再邀请……**

## 四、三个根因的代码位置

### 根因 1：音频 SETUP 被车机 400 拒绝（触发源）

```
[14:57:10.870] AIRPLAY: 音频 SETUP 往返 2056ms [RTSP/1.0 400 Bad Request]
[14:57:13.134] AIRPLAY: 音频 SETUP 往返 2261ms [RTSP/1.0 400 Bad Request]
[14:57:15.165] AIRPLAY: 音频 SETUP 往返 2030ms [RTSP/1.0 400 Bad Request]
[14:57:15.166] AUDIO: 全部候选档位协商失败（共 3 档）——本次仅推视频
```

三档都试了（AAC-LC 48k / PCM 48k media / PCM 48k compatibility），全是 **400 Bad Request**——
不是"不支持这个格式"（那会是 4xx 里的其他码或 415），是**请求本身不被接受**。每次还要 2 秒。

视频 SETUP 是成功的（`SETUP 完成 eventPort=5001 timingPort=6020`），所以只有音频这一步有问题。

**推断**（未验证）：车机把音频视为会话必需项，3 次失败后判断会话不完整，于是发 ctrl 邀请。
时间上也对得上：音频放弃在 14:57:15，车机第一次邀请在 14:57:28（13 秒后）。

### 根因 2：推流中收到 ctrl 邀请被直接丢弃（第一次黑屏的直接原因）

`SessionController.onCtrlInvite()` 第一行：

```kotlin
private fun onCtrlInvite(receiverId: String?) {
    if (!sessionWanted || connectCancelled || isStreaming()) return   // ← 推流中什么都不做
    ...
}
```

注释写的是「忙（正在连/已在推流）时什么都不做，让在跑的那轮自己走完」。

**这个假设在 ID7 上不成立**：车机发邀请不是"帮你重连"，是"**我要重建，请你配合**"。
不配合的结局是它等 18 秒后自己拆——它拆的是我们正在推流的那条会话。

日志对照（两次邀请，两条不同分支）：

```
[14:57:28.487] ✓ 车机 ctrl 邀请（第 1 次…）——AirPlay 窗口已开启     ← 推流中，只回了 200 OK
[14:57:46.477] EVENT: 读取结束 - Connection reset                  ← 18 秒后车机拆会话

[14:57:50.614] ✓ 车机 ctrl 邀请（第 2 次…）——AirPlay 窗口已开启
[14:57:50.615] CTRL: 车机邀请到达…且当前空闲——立即发起一轮连接        ← 断完了，才走重连
```

### 根因 3：重连首帧不是 IDR（让循环无法自愈）

`VideoSender.startPassthrough()`（新一轮会话，`VideoSender.kt:410`）：

```kotlin
cachedCsd = null
sentSps = null
configSent = false
awaitingKeyFrameAfterRestart = false      // ← 关键：新会话不要求等 IDR
```

紧接着 `CarLifeHijack.attach()`（`CarLifeHijack.kt:404`）在会话建立后被调用：

```kotlin
spsPps?.let { videoSender.seedCsd(it) }   // ← 把 cachedCsd 又填回来，日志"已用缓存 SPS/PPS 预置 csd"
val pending = ...                          // 从 GOP 缓存取历史帧
for ((data, key) in pending) { videoSender.submitH264(data, key) }
```

**注意 `pending` 经常是空的**：`gop` 只在收到 `keyFrame=true` 的帧时才 `clear()` 后重新攒
（`CarLifeHijack.kt:728`），非关键帧在缓存为空时直接被丢掉。断流到重连之间那 3 秒里
如果没有 I 帧落在缓存里，`pending` 就是空列表——于是**送给车机的"首帧"其实是 attach 之后
实时流里的下一帧，它八成是 P 帧**。日志时间差也印证：`53.876` attach → `53.907` 首帧，
只隔 31ms（≈52fps 的帧间隔），不是历史缓存帧。

配合 `submitH264()` 的兜底分支：

```kotlin
if (!configSent) {
    if (hasSps) { sendConfigFromNals(...) }
    else {
        val csd = cachedCsd
        if (csd != null) {
            log("VIDEO: 新 IDR 未携带 SPS/PPS——用缓存 csd 重发 VideoConfig")
            sendConfigFromNals(csd, output)     // ← 用旧 csd 拼 config
        }
    }
}
sendFrameFromNals(nalUnits, keyFrame, output)   // ← 然后把这个 P 帧当首帧发出去
```

而 `cachedCsd` 之所以不是 null，是因为 attach 里的 `seedCsd()` 又把缓存 SPS/PPS 填了回来。
那个函数的设计意图写得很清楚：

> 用于「车机重新接上通道、但手上没有带 SPS 的关键帧」…预置后第一帧（哪怕是 P 帧）
> 就能把 config 发出去，最快一个 IDR 周期就有画面。

**这个前提对 ID7 不成立。** 新建的数据通道 = 新建的 SETUP = 全新的解码器，它手上一帧都没有，
必须等 IDR。送 P 帧进去，解码器直接报错，车机选择断开整轮会话而不是丢帧静等。

⚠️ 注意：日志里那句 `新 IDR 未携带 SPS/PPS` 是**误导性措辞**——那帧 NAL 类型是 1，根本
不是 IDR（IDR 是 5）。看日志时容易被这句话带偏，以为送的是关键帧。

## 五、为什么 Audi / DiPlay 能跑，ID7 不能

同一个包在奥迪 MIB3 和 DiPlay 测试台上是正常的，说明这三处不是"绝对错误"，而是
**在 ID7 上不被容忍的实现选择**：

| 我们的做法 | Audi / DiPlay 的反应 | ID7 的反应 |
|---|---|---|
| 推流中忽略 ctrl 邀请 | 不主动发邀请，没触发过 | 发邀请 → 等 18s → **拆会话** |
| 用缓存 csd 拼 config + 送 P 帧当首帧 | 丢几帧，等下一个 IDR 自己恢复 | **整轮会话断开** |
| 音频协商失败就放弃，只推视频 | 能接受，画面照出 | 认为会话不完整，**要求重建** |

ID7 是 Cinemo 组件栈（`CinemoBTComponent` / `CinemoWIFIComponent` / `CinemoHIDRemote`），
对会话完整性比 Delphi（奥迪）严格。

## 六、关于「重启」：不是崩溃

日志里三次 `===== 进程启动 =====`：

| 时刻 | 性质 |
|---|---|
| 14:46:44 | 正常启动 |
| 14:56:53 | **看不出原因**（前一段日志被 2MB 上限截断，14:56:44 还在正常推流） |
| 15:06:58 | **设计行为**：15:06:38 `IDLE: 车机已远离（蓝牙断开 30 秒未回连）——结束会话…随后退出进程`，20 秒后被车机靠近检测重新拉起 |

`IDLE` 那条退出是「车机远离 30 秒自动收摊」的正常逻辑，`APPROACH` 又把 App 拉起来——
所以看到的"重启"多数不是崩溃，是**车机蓝牙断开 → 自动退出 → 靠近又自动启动**。

日志里**没有任何 Java 崩溃栈、没有 ANR、没有 SIGSEGV/OutOfMemory**。真正的异常只有断流本身。

## 七、修复建议（按性价比排序）

### 1. 新会话必须等 IDR（必改，成本最低）

`startPassthrough()` 里把 `awaitingKeyFrameAfterRestart = true`。
预置 `cachedCsd` 只允许"提前把 VideoConfig 发出去"，**不能因此放行 P 帧**。
判据：新会话开流后若首帧 NAL≠5，就丢弃并等——日志会打 `已跳过 N 个非关键帧`。

代价：重连后要等 CarLife 引擎下一个 I 帧（实测 I 帧间隔约 2 秒 / 120 帧），即多等 ≤2 秒。
收益：**8 次 0.06 秒的秒断全部消失**，这是循环里最大的一块。

### 2. 推流中收到 ctrl 邀请要当回事（必改）

不能直接 `return`。至少三件事：
- 记一行日志（现在完全静默，排障时看不到车机来过）；
- 起一个短定时器，若 N 秒内没有新的邀请就把会话作废重建（而不是等车机来拆）；
- 更要紧的是先查**为什么车机会发邀请**（见下条）。

### 3. 查音频 SETUP 的 400（触发源，优先级最高但成本最高）

三档全 400 说明请求体本身有问题，不是格式不匹配。下一步：
- 把三次 SETUP 的**完整请求体**（bplist 解码后）打出来，逐字段对比视频 SETUP 成功的那份；
- 重点看 `streams[].type`、`dataPort`、`controlPort`、`audioFormat`、`ct`/`sr`/`spf` 字段；
- 对照 ID7 `/info` 里 `audioFormats[]` 的 9 档（日志已打印完整位掩码），确认我们选的档是它
  真正支持的那一档——目前试的 3 档都是我们**自己**挑的，不是从它的清单里反查出来的；
- 顺带：`0x8000` 这个值在日志里既被当作 `format` 又被当作 `audioType`（
  `audioType=media format=0x8000`），可能是把位掩码当格式用了，值得核一下。

## 八、这次日志顺带确认的事（对 ID 系列连接有意义）

1. **ID7 确实用 Cinemo 组件**，与别克的 CarPlay 中间件同源（`CinemoBTComponent` /
   `CinemoWIFIComponent` / `CinemoHIDRemote`），但 manufacturer 是 Volkswagen、model VW4131。
2. **车机 0x1D01 发送清单只有 14 条**，且**没有 `0xEA03`**：

   → 这份清单只覆盖「车机能发」，EA 族是否可用仍要实车试（见 `vw-id7-control-feasibility.md`）。
3. **连接配置实际跑的是「通用（标准）」**，不是「大众 ID（MEB ICAS3）」——
   14:56:53 那轮用户切过档（`连接配置改为「大众 ID」`），但 15:07:50 起的重连全部记
   `BT-C: 连接配置=通用（标准）`。所以本次日志**没有验证到 1.2.17 新档位**。
4. **/info 实测**：`displays[0] = 2240×976 @60fps`，与 VideoConfig 声明一致；SPS 是 1280×720

   **这不是黑屏原因**——别照着"声明与码流不一致"去改，2026-10-25 已经这么改过并在真机回滚。
5. **CarPlay 会话建立是通的**：`/info` 48KB 应答、SETUP、RECORD、`VideoConfig avcC=32B`、
   首帧送达、`RECORD 完成——会话已激活` 全部正常。问题只在"会话能不能活下去"。
