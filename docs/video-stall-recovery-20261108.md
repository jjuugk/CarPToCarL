# 画面停摆：分级干预 + 判据修正（2026-11-08）

> **2026-11-10 已移除「分级干预」部分**：设置页开关、`StallJudge` / `StallRecoveryPrefs`、
> 8s 重建编码器与 30s 重建会话全部删除，看门狗退回「只观测」。原因见 2026-11-10 真机日志：
> 引擎退出（7240 未监听）后干预没有任何接管者，仍按 8s 节奏刷「请求重建编码器」，把
> 「引擎不在」的空白期写成了「正在恢复」；30s 阈值还会翻倍（30→60→120），越到后面越救不到。
> 本文**只作历史记录保留**，当前的判据与实现以 `CarLifeHijack.startStallWatchdog()` 为准
> （判据仍是「最后一帧距今」，这部分的结论依然有效）。

来源：对比同源项目 **AMCar 1.0.48**（`cnb.cool/xi_zhu/AuDiCar`，`AMCar` 分支）的
`CarLifeHijack.startStallWatchdog()`。两边画面骨架同源，差异集中在「画面冻住之后怎么办」。

## 1. 改了什么

### ① 判据：从「2 秒窗口帧数」改成「最后一帧距今」

旧判据：`STALL_POLL_MILLIS`（2s）窗口内少于 4 帧（≈2fps）就算停摆。

问题：来电 / 语音接管期间，引擎会降到 **0.8fps 心跳帧**（只维持画面不黑，不出新 IDR）。
0.8fps 在 2 秒里只有约 1.6 帧 → **旧判据必然把它判成停摆**。AMCar 的实车日志里这正是
「通话中我们自己把黑屏拖长」的原因：判成停摆 → 重建编码器 → 30~45 秒才出首个 IDR。

新判据：`frameAgeMs(lastSourceFrameAt, now)`，心跳帧距上一帧只有 ~1.25 秒，不触发；
真冻住的引擎一帧都没有，8 秒后照旧触发。`-1`（本轮一帧都没收到）继续按「不判」处理，
否则引擎刚起来就被拆。

旧判据保留在 `StallRecoveryPrefs.judgeByFrameAge = false` 后面，可一键回退。

### ② 行为：从「只观测」改成「分级干预」

| 停摆时长 | 动作 | 代价 |
|---|---|---|
| 8s | `requestVideoReinit()` 请求引擎重建编码器 | 约 1 秒后吐 SPS+IDR |
| 每 8s | 再轻推一次（引擎常要推两三次才吐 IDR） | 同上 |
| 30s（翻倍、封顶 120s） | `client.stop()` 强制重建 CarLife 会话 | 引擎冷启动 30~45s 才出首个 IDR |

依据：AMCar 1.0.15 的真机结论——旧实现「只观测不干预」时停摆最长拖到 **128 秒**，
而且每次自然恢复都伴随一次新会话，说明重建会话才是有效手段。

**两处刻意的保留：**

1. **通话中不干预**（`AudioManager` 的 `MODE_IN_CALL` / `MODE_IN_COMMUNICATION` /
   `MODE_RINGTONE`）。旧注释「通话期间根本没有画面可编，硬重建只会把水搅浑」在通话期
   仍然成立，加上判据修正，现在是两道保险而不是一道。
2. **同一次停摆只拆一次会话**（`interventions == 2` 后不再动手）。连续拆会把引擎永远
   按在热身期，比不干预更糟。

### ③ 观测：写卡死单独记账

`VideoSender.noteWriteStall()`：`output.write()` 一旦永久阻塞（接收端不读、链路被打满），
这一帧永远不返回，既不会进「已发送 N 帧」，也不会触发任何写失败判定——日志上跟
「引擎没出帧」长得一模一样，而两者处置相反。

实现：帧写路径在**进锁之前**打 `writeStartedAt`、`finally` 清零；看门狗每 2 秒问一次，
超过 3 秒没返回就记一行（同一笔最多每 5 秒喊一次）：

```
VIDEO: ⚠ 帧写入已阻塞 9.0s（这一笔还没返回）——接收端不读或链路被打满，画面会冻在最后一帧
```

标记打在进锁之前是刻意的：等锁的时间同样属于「这一笔还没飞出去」。

### ④ 日志：停摆时带手机屏幕状态

`screenStateText()` 只读 `PowerManager.isInteractive` / `KeyguardManager.isKeyguardLocked`，
不需要任何权限。用来把「手机侧画面被占用」和「链路/引擎问题」分开——2026-10-29 那次实测
停摆时屏幕是亮的，旧注释的「锁屏」假设并不成立。

## 2. 开关

设置页「画面停摆自动恢复」（`switchStallRecovery`，默认**开**）：

- 开 = 上面 ①②③④ 全生效；
- 关 = 回到旧行为：只记日志，不重建编码器、不重建会话（判据仍是新的，只少了一条噪音）。

偏好键：`settings` → `video_stall_recovery`；判据键 `video_stall_by_frame_age`（无界面，
默认 true）。两者都在**看门狗线程启动时**读一次，运行中改要等下次引擎重连才生效——
避免同一次停摆前后用两套标准。

## 3. 没抄的部分

| AMCar 有的 | 为什么不抄 |
|---|---|
| 魅族 20fps→60fps GL 重编码（`CarLifeReEncoder`，674 行） | 只服务一家 ROM，GPU/EGL 代码出错面大 |
| `BitrateController` 自适应码率 | 编码器在 CarLife 引擎里，`setParameters` 改不动源码率，实际是死代码（他们自己默认也关） |
| `StatusCard` 顶住画面（`hold=true` 丢弃真实帧） | 我们的场景是「没画面」，不是「要盖住画面」，现有 `NoticeFrameEncoder` 够用 |

反过来我们有、他们没有的：`VideoDeliveryGate`（帧龄+背压，结构性积压才跳 IDR）、
`FirstFramePolicy`（按策略回放缓存 GOP）。

## 4. 验证

- 单测：新增 `StallJudgeTest`（7 例）——判据哨兵、8 秒边界、轻推节流、30 秒拆会话、
  已拆过不再拆、阈值翻倍封顶；
- `:app:assembleRelease` 通过，全量单测 0 失败；
- 实车看点：冻住 8 秒后日志出现 `CARLIFE: 停摆 8 秒——请求引擎重建编码器`；
  30 秒后出现 `强制重建 CarLife 会话`；通话中只出现停摆日志、**不出现**上面两条。
