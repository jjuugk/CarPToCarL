# 奥迪 MIB3 · 2026-11-04 实车：EA 数据把 iAP2 链路拖死 + 首连音乐无声

> 样本：`CarPToCarL-log-20261104-083034.txt`（1.2.17 / main），车机 `Audi_MMI_8349`
> （`AUDI 4260` / `DELPHI` / MIB3H，MAC `10:E8:A7:81:29:6B`），手机 HONOR PTP-AN10。
> 现象（用户口述）：首次连上「导航有声音、音乐没声音」，断开重连后正常；
> 「车机控制读不到数据」。

## 一、一句话结论

两个症状**根因不同**，但都在这份日志里被钉死了：

1. **车机控制读不到数据**：面板在 EA 会话（0xEA03）还没建立时就往隧道写 0xEA04（viwi
   JSON）。车机从那一个包起**再也不 ACK**，约 33~37 秒后被我们的重传看门狗判
   `packet 115 not acknowledged` 把整条 iAP2 链路拆掉；而 CarPlay 还在跑，出站重连被
   「会话期间静音」闸门挡住 —— 于是这一整场会话再没人把控制链路连回来。
2. **首连音乐无声**：音频流 SETUP 完成后先静默了 65 秒（车机上没人放音乐），第一段音乐
   原样编码发出去了但车机不放；重连后的会话里音频流一建立 0.4 秒就有包，同样的音乐
   立刻正常。差别只有「流建立后先空转了多久」。

## 二、证据链：三轮会话死在同一个序号

| 轮次 | BT iAP2 连入 | 首个 0xEA04（只读 GET） | 链路被拆 | 死因 |
| --- | --- | --- | --- | --- |
| 1 | 08:26:10.956 | 08:26:23.419 | 08:26:56.975 | `packet 115 not acknowledged` |
| 2 | 08:28:32.064 | 08:28:46.126 | 08:29:23.470 | 同上 |
| 3 | 08:29:34.959 | 08:29:48.331 | 08:30:23.406 | 同上 |

三轮都是**同一个序号 115**，这本身就说明「死因是固定的一条消息」。第 3 轮因为
`LINK tx` 日志还没打满上限，完整拍到了现场：

```
[08:29:38.176] iap2 tx=0x4300（发后不管）        ← seq 113
[08:29:38.177] iap2 tx=0x4e0e（发后不管）        ← seq 114
[08:29:38.260] LINK rx: ctl=0x40 seq=6 ack=114    ← 车机最后一次 ACK
[08:29:48.331] MIB3: 已发 8 条只读 GET
[08:29:51.330] LINK tx: ctl=0x40 seq=115 ... ea 04 {"id":1,"method":"GET","path":"/vehicleinformation"}
[08:29:51.332] LINK tx: ctl=0x40 seq=116 ... ea 04 {"id":2,...}
   ...（115~122，8 条 viwi GET）
[08:30:23.406] LINK closed: packet 115 not acknowledged
```

`ack=114` 之后再没有任何 `LINK rx`。也就是说：**第一个 0xEA04 落地的那一刻，车机的
iAP2 协议栈就停止确认了**（不是丢一个包，是整条链路不再 ACK）。

同一份日志里 0xEA03 **一次都没有**（三轮 grep 全空），面板三轮都停在
「等待 0xEA03 会话状态」——即 EA 会话自始至终没建起来，这些 0xEA04 是往一条不存在的
管道里灌字节。旧代码是**故意**允许这么干的：

```kotlin
// Mib3ControlLink.refreshReadOnly()（1.2.17）
// 即使还没 0xEA03 也允许发只读 GET：读不会改变车辆状态，而早点把请求送上
// 去有助于让车机把隧道激活（真机首次连接时它可能只是还没回执）。
```

这个「早点送上去激活隧道」的假设，被这台车证伪了，代价是整条控制链路。

## 三、为什么 0xEA00 只发给了 eadata1

车机在 0x1D01 里声明了**三个** EA 协议：

```
00 2b 00 0a | 00 05 00 00 01 | 00 23 00 01 "de.audi.mmiconnectdatatransfer"
00 2b 00 0a | 00 05 00 00 02 | 00 19 00 01 "com.audi.cpp.eadata0"
00 2b 00 0a | 00 05 00 00 03 | 00 19 00 01 "com.audi.cpp.eadata1"
```

三个槽**都用参数号 10**。旧解析 `associateBy { it.id }` 把它当唯一键，只留下最后一个，
于是只对 `eadata1` 发了 0xEA00（日志只有一行 `EA 组件[10] protocol=3`）。而按设计
数据该走 `eadata0`（协议号 2）。车机对一个它不当成数据口的会话不回 0xEA03，完全可以
理解。

## 四、这一轮改了什么

| # | 改动 | 位置 |
| --- | --- | --- |
| 1 | EA 协议清单按「参数号可重复」解析，三个槽全部收集；0xEA00 对每个都发 | `iap2/Iap2Csm.kt`（新增 `Iap2Ea.parseProtocols`，可单测）+ `Iap2SenderSession.parseEaProtocols` |
| 2 | **0xEA03 之前禁止写 0xEA04**：面板的只读拉取改成先看 `Phase.READY`，没就绪只记日志并挂待办；0xEA03 一到自动补发那一轮 | `mib3/Mib3ControlLink.kt`（`refreshReadOnly` / `pendingRefreshOnReady` / `samplesFromStatus`） |
| 3 | 0xEA00 是「发后不管」，8 秒内没等到 0xEA03 就再催一轮（一次为限） | `iap2/Iap2SenderSession.kt`（`scheduleEaSessionRetry`） |
| 4 | **控制链路中途掉线要能自愈**：CarPlay 期间不再无条件静音出站，只对掉线那一台补连，最长 180 秒 | `bt/Iap2BluetoothClient.kt` + `BtSessionGate.linkLostPeerAddress` |
| 5 | 音频流静音保活：超过 300ms 没有真实 PCM 就按实时速率补静音帧 | `audio/AudioSender.kt`（`startSilenceKeepAlive`） |

第 4 条独立于前三条：即便车机以后因为别的原因停 ACK，也不会再出现「画面声音都在、
控制数据永久失联、只能手动断开重连」这种状态。

## 五、音频那一条（仍是假设，但改法是标准动作）

第 1 轮的音频时间线：

| 时刻 | 事件 |
| --- | --- |
| 08:26:19.751 | 音频流协商成功（t102/media AAC 44100，latency 250ms） |
| 08:26:19.815 | 流加入会话，补发 RECORD |
| —— | **65 秒没有任何音频包** |
| 08:27:24.976 | 导航 TTS（16k 单声道）到达 → 有声 |
| 08:27:39.216 | 媒体 44.1k 立体声开始，`音频直通 216 包/1411kbps 电平 99%` |
| 08:28:29.6 | 用户手动断开（共发 2583 包，≈60 秒音频，与「TTS 5s + 音乐 50s」吻合） |
| 08:28:41 | 重连后音频流 0.4 秒就有包 → 音乐正常 |

同样的编码器、同样的端口、同样的负载封装，唯一差别是「流建立后空转了 65 秒」。
真 iPhone 的音频流是连续的（没声音也送静音帧），接收端据此维持解码/播放管线与
RTP↔NTP 时钟；空转一分钟后突然来音频，管线早被判空闲。

所以第 5 条是：**没有真实 PCM 时按实时速率补静音帧**，真实 PCM 一到立刻停补。
代价是空闲时约 43 包/秒、每包十几字节（AAC 静音），可忽略；好处顺带覆盖
「音乐暂停 → 再播放」「来电恢复」这几条同样容易断流的路径。

> 待验证：如果这一版上车后「首连音乐仍无声」，说明车机丢的是别的东西
> （RTP 时间戳基准 / 音量 / 音频通路选择），下一步该看车机侧的 `/feedback`
> `sampleTime` 是否在推进，以及是否需要 `SETRATE`/`FLUSH`。

## 六、上车验证清单（按顺序看日志）

1. `iap2 0x1d01 EA 组件[10]` 应该出现**三行**（protocol=1/2/3），不再是只一行 protocol=3。
2. `EA: 数据通道协议 = com.audi.cpp.eadata0`（协议号 2），不是 eadata1。
3. 出现 `iap2 rx=0xea03 EASessionStatus` → 面板「链路」行变 `EA 隧道已建立`，
   紧接着 `MIB3: 0xEA03 已到——补发被挡下的那轮只读 GET`。
4. `LINK closed: packet 115 not acknowledged` **不再出现**；即使出现，也应紧跟一行
   `BT-C: CarPlay 会话仍在，但 iAP2 控制链路已断……只对它单独补连`，然后
   `BT-C: ✓ 已连入 …` 自动恢复。
5. 连接后先别放音乐，等 30 秒以上再放：应听到 `AUDIO: 无 PCM 超过 300ms——开始补静音帧保活`，
   随后音乐直接有声。

## 七、还没解决的

- 0xEA03 到底是不是「只要协议对就会回」，要在车上验。若三个协议都发了仍然静默，
  下一步按 `docs/mib3-control-handover.md` 的梯子走：换消息号 → 换载荷形态 → 换封帧 →
  回头重读逆向材料（车机的 EA 栈可能要求先应答它发来的 `0xEA02 RequestAppLaunch
  cn.audi.connect`，日志里这条一直是「未处理的 CSM」）。
- 车机 `controlPort 6011` 全程 ICMP 端口不可达（同步包 130/133 被拒），三轮都一样，
  目前判断与「有没有声音」无关（第 2、3 轮有声时同样被拒），但 Sync 锚点实际等于没有，
  以后调音画同步时要记得这一点。
