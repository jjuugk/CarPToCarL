# 大众 ID7（MEB ICAS3）CarPlay 车辆控制可行性评估

> 评估对象：`大众id7，CarPlay控制方式与协议总结.txt`（ICAS3CN / `ICAS3GP_CN4_VW_R4220L` /
> MU 6422 / 1.422.4 / Exynos Auto V9 / Apple CarPlay 栈 320.17.7 + iAP2 3.0）
> 问题：**能不能照 MIB3 的路子，做 ID 系列（MEB）的车辆控制？**
> 结论日期：2026-11-03 · 纯分析，不含代码改动

---

## 一、结论先说

**不能。而且这次不是"资料不够"，是这份文档把"为什么不能"写清楚了。**

CarPlay 是「手机渲染、车机只解码上屏」的投屏协议。它对车身的数据接口是**单向、只读、且极窄**的：
车机愿意的时候，把 ETC 状态、导航辅助驾驶状态、供电来源这几种东西告诉手机；
反过来，手机没有任何一条能碰到执行器（空调/车窗/车门/座椅/灯光）的消息。

把问题拆成两个不同的"控制"，答案才清楚：

| 问题 | 答案 | 现状 |
|---|---|---|
| **A. 我们（模拟 iPhone）能不能控制车机功能** | **不能**，协议里没有这条路 | 本报告主体 |
| **B. 车机能不能控制我们的界面**（切前台、昼夜、限屏、触摸注入） | **能**，而且已经在做 | 现有代码已覆盖，见第六节 |

MIB3 之所以能控，不是因为它比 ID7 更"开放"，而是因为**奥迪在 EA 隧道后面留了一个 HTTP/JSON 后门**
（`127.0.0.1:14751` 的 viwi，ACL 档位 `ext_devices` 对 27 个端点全开）。那是设计者给外部配件
留的门。**ID7 这份文档里没有等价的任何东西**——不是门锁着，是没看到门。

## 二、文档自己给出的四条硬证据

### 证据 1：第 12.2 节直接写死了

> (1) CarPlay 不开放车身控制。没有空调/车窗/座椅/灯光控制消息。
> `updateVehicleInformation` 只是"车机告知手机车辆状态"，不是"手机控制车辆"。

这段不是推断，是作者基于整份固件静态分析下的结论。它跟我们 2026-11-03 在 MIB3 上得到的
结论完全一致（见 `CarPToCarL/docs/mib3-viwi-control.md`）：**iAP2 里就不存在车辆控制消息**。

### 证据 2：74 条消息逐条看，没有一条是执行器

文档 4.1 的表列了车机全部 `send*` 消息（74 条）。按功能归类：

| 类别 | 消息 | 能控车？ |
|---|---|---|
| 会话/认证/识别 | `0x4301` `0xAA0x` `0x1D0x` `0xEA0x` | 否 |
| 显示/输入 | `0x6800~0x6803` HID | 否，控的是手机上的指针 |
| 电话 | `0x415x` `0x417x` | 否，控的是手机通话 |
| 媒体 | `0x4C0x` `0x500x` | 否 |
| 导航 | `0x5200` `0x5203` | 否，且**只有手机→车机单向**（8.4） |
| 蓝牙/Wi-Fi | `0x4E0x` `0x570x` | 否 |
| 电源 | `0xAExx` | 否，只上报供电来源 |
| 车辆状态 | `0xA101` | 否，**车机→手机单向** |
| 位置/VoiceOver/辅助触控/App | `0xFFFx` `0x56xx` `0x54xx` `0xADxx` | 否 |

**没有空调、没有车窗、没有车门锁、没有座椅、没有灯光。** 一条都没有。

### 证据 3：就算能双向，能传的字段也窄得可怜

9.7 节 `updateVehicleInformation` 的三个字段：

```
electricTollCollection { active }      // ETC 是否在工作
navigationAidDriving   { active }      // 辅助驾驶是否在接管
userPreferences        { touchpadSettings }  // 用户触摸板偏好
```

**连车速都没有。** 车速在车机侧走的是完全另一条路：`/rsi/carplaysvc_displayspeed.cpp` 的
`DisplaySpeedClient::subscribeDisplaySpeed`（7.4 / 9.6），不经过 CarPlay。

一个只有「ETC 开没开」的通道，即便给它双向能力，也控制不了任何东西。

### 证据 4：连对手机的控制都没有强制力

> (4) 控制命令都要手机配合。车机发 `requestUI`，手机可以拒绝；没有强制力。

这说明 CarPlay 的控制模型是**协商式**的，不是命令式的。这种模型下不可能存在
"发一条报文就开空调"的设计。

## 三、容易误判的三处（下次别再绕进来）

### ① `iAPSendMessage`（5.2）看起来像万能透传

> `iAPSendMessage` — `data` (bytes) — 透传 iAP2 消息

看着像"可以给对端塞任意 iAP2 消息"。但两点都要看清：

- **方向是车机 → 手机**（12.1 方向表把它列在「车机 → 手机」那一栏）。我们作为手机侧，
  拿不到这个 API 的发送权。
- 即便能发也没用：iAP2 本身没有车身控制消息（证据 1）。透传一个不存在的消息，等于透传空。

这条最容易被当成"后门"，实际上两个方向都堵死。

### ② 第 7 章标题叫「控制通道 D: 车机内部总线」

这章内容最"香"——`kipc/carplaysvc_can.cpp`（车速/挡位/灯光）、`carplaysvc_power.cpp`、
SOME/IP（`p_carplay`）、RSI（车速订阅）。看到 `carplaysvc_can.cpp` 很容易想到
"这不就是车身信号吗，从这儿控"。

**但它是 HMI ↔ carplay 进程之间的通道**（7.1 分层图：HMI → KIPC → carplay 进程 →
libAirPlay.so → 手机）。手机在链路的最远端，跟 KIPC 之间隔着整个 carplay 进程和 AirPlay 协议栈。
`kipc::Interface::send_pkt(...)` 是进程内的 C++ 调用，不是网络报文。

**MIB3 那套能成，恰恰是因为 viwi 是 HTTP/JSON 且监听在 `127.0.0.1:14751` 这种"可被桥接"的形态。**
ID7 的内部总线是 SPI/共享内存/CAN + SOME/IP + WebSocket，没有一个是文档里描述为"对外暴露"的。

### ③ `updateVehicleInformation` 名字的方向迷惑性

英文名看起来像"（手机）上报车辆信息给（车机）"，中文语感更像"更新车辆信息"。实际是
**车机告诉手机**，且内容只有证据 3 那三项。名字和方向无关，看 12.1 方向表为准。

## 四、唯一一个「手机 → 车机」的真实动作

8.6 节，这是全文档里**唯一**一条手机发起、车机侧产生物理效果的请求：

```
iPhone → AirPlay 回调 handleDisableBluetooth(dict)
       → carplay → BT 栈 (bluego) → 车机 BT 关闭/断开
固件字符串: "Carplay request disconnect BT with sendReqDisableBT"
```

它有三重意义：

1. **证明「手机 → 车机」不是绝对的空集**——存在一条从手机侧发起、能改变车机状态的路径；
2. 但它**不是通用命令通道**：只是一个特定通知，效果只有"关蓝牙"；
3. 它是文档里唯一可复现的"让车机做事"的探针。**如果将来要证明"手机能不能驱动车机"，
   这是第一个该试的**，而不是去猜 EA 数据帧。

限制：文档没说这条通知在 AirPlay 协议里的**具体报文形态**（哪个端点、什么字段），
属于【未闭环】。它记在"iPhone 原生栈行为"上，我们模拟 iPhone 时能否发出、发成什么样，
需要实车抓包。

## 五、如果一定要做，只剩这五条路（按性价比排序）

前提：**控制入口不在 CarPlay 里**。所以下面全部是"在 CarPlay 之外找车机暴露给外部的服务"，
思路与 MIB3 完全一致——找后门，不找协议。

### 路径 1：EA 会话探测（成本最低，代码现成）★ 建议先做

**为什么值得试**：文档 4.1 的 74 条是车机**能发**的消息（`send*` API），不是车机的完整能力表。
里面出现了 `0xEA03 SessionExtAccessoryProto sendStatusExternalAccessoryProtocolSession`——
说明**车机具备 EA 会话的状态回执机制**。但 `EA00`（开会话）/`EA01`（关会话）不在表里，
因为它们是车机**收**的消息，这份表不覆盖。

所以「ID7 有没有 EA 通路」这个问题，**这份文档既不能证明有，也不能证明无**，只能实车试。
这一条我在上一版报告里差点写成"ID7 没有 EA 数据帧"，是过头的——那张表只覆盖单向。

**怎么做**：用 `main` 分支的 1.2.15 包（`switch-pool` 上没有 EA 代码），连上 ID7 后打开
「MIB3 车机控制」面板，看「链路」区的 EA 状态：

- **收到 `0xEA03`** → EA 会话机制活着，接着试 `0xEA04` 灌数据；
- **完全死寂** → EA 通路不存在或协议号不对，这条路作废，转路径 2。

**但要有心理准备**：即使 EA 会话建起来了，**MIB3 那套也搬不过来**——因为 MIB3 的关键不是
EA 会话，是会话背后桥接的 viwi 总线。ID7 的 EA 会话后面接什么，文档里没有任何线索。
**没有目标总线，会话建起来也只是条空管子。**

### 路径 2：wlap5 同网段的端口横向探测（成本低，纯侦察）★ 建议同时做

**依据**：无线 CarPlay 时车机自建 5GHz AP `wlap5`，`10.173.189.1/24`，内置 DHCP（2.2）。
手机连上后**与车机在同一网段**，这是难得的"进了内网"状态。

**关键疑点**：2.1 节列的开放端口（7000 / 5000-5001 / 6030 / UDP 5001/5020/6000/6003/6011/5353）
出自 `firewall_rules.IPv4`，但文档**没有区分 ncm0（有线）与 wlap5（无线）**，只在 UDP 5001
标注了"ncm0 单独放行"。**无线侧的规则集是否更宽松，是未知的。**

**怎么做**：无线 CarPlay 连上后，从手机扫 `10.173.189.1` 的 TCP 端口
（22 / 23 / 80 / 443 / 7000 / 8080 / 9090 / 30490 / 5555 等），再扫 UDP 30490（SOME/IP-SD）。

**判据**：

- 只有 7000/5000/6030 开着 → 白名单严格，此路不通，转路径 3；
- 出现白名单外的端口 → **有戏**，逐个看是什么服务（横幅/HTTP 响应即可判断）。

这条是**整个评估里最该先做的一步**，因为成本最低、信息量最大，且不需要改任何代码。

### 路径 3：SOME/IP 服务发现（理论价值最高，成本中等）

**依据与风险都要说清**：7.3 节实证 `VSOMEIP_APPLICATION_NAME = p_carplay`、走以太网。
MEB 是服务化架构（这是平台设计的常识，**不是这份文档的证据**），空调/车门这类功能在 MEB 上
大概率是 SOME/IP 服务。

**但文档里没有一个字说 SOME/IP 服务对 wlap5 暴露。** 这纯属推测。

**怎么做**：wlap5 上监听 UDP 30490 的 SOME/IP-SD 组播，看有没有服务公告（`OfferService`），
列出 serviceId/instanceId。有公告再用 Python 的 `someipy` 之类的库发 `FindService` + 方法调用。

**难点**：SOME/IP-SD 通常只在车内以太网内网，AP 侧多半不放行；且需要服务 ID 表才能发对方法。

### 路径 4：RSI / SAI 的 WebSocket（只读，价值有限）

7.4 节有 `/rsi/carplaysvc_displayspeed.cpp`（车速订阅），13.x 提到 RSI 走 WebSocket。
若它监听的端口在 wlap5 可达，最乐观也就是**读到车速**——只读，不是控制。
除非 RSI 同时暴露了写接口，而文档没有这种迹象。

顺带：这条即便成了，价值也只是"拿车速做分心限制"，不是用户想要的控车。

### 路径 5：Android VM（最后考虑）

1.1 节提到平台是 QNX + LGE Linux(IVI) + **Android VM**。如果 VM 有 adb over network 或
某些服务暴露在 wlap5 上，理论上可以进去。**零证据，风险高，不建议优先。**

## 六、对现有代码的影响：不用改

| 项 | 结论 |
|---|---|
| `switch-pool` 1.2.17 的「大众 ID（MEB ICAS3）」档位 | **不需要为控制做任何改动**。它解决的是**连接**问题（补发 `0x1D01` 识别帧），与控制无关 |
| `main` 1.2.15 的 MIB3 控制面板 | ID7 上**没有对应后端**，面板会一直停在「链路未就绪」。可以当 EA 探测工具用（路径 1），但别指望它控车 |
| `Iap2MessageIds` 里的 `0xA100/0xA101` | 常量是对的，但 ID7 上方向是车机→手机，拿不到控制权 |
| 新写 ID7 专用代码 | **不建议**。没有已验证的入口，写出来就是一堆猜的封帧 |

一句话：**这份文档的价值不是"能做"，而是"明确告诉你不用在这上面花时间"，并且给出了
三条真正值得探的方向。**

## 七、对比 MIB3：为什么同一套思路在 ID7 上无从下手

| 维度 | 奥迪 MIB3（能做） | 大众 ID7（不能做） |
|---|---|---|
| 车机给的入口 | EA 隧道 → viwi `127.0.0.1:14751` | 文档中无任何等价物 |
| 入口形态 | HTTP/JSON，每行一条，好封帧 | KIPC(SPI/SHM/CAN) + SOME/IP + RSI，全是内部 IPC |
| 鉴权 | `token_enforcement.enabled=false`，ACL `ext_devices` 全开 | 不涉及（够不到） |
| 端点证据 | 27 个端点逐条列出（`/hvac` `/door` `/window` …） | 无 |
| 可达性 | 手机 → EA 会话 → 本地回环，一条链打通 | 手机与内部总线之间隔着整个 carplay 进程 |
| 结论 | 找的是**车机留的后门** | **没看到后门** |

**关键认知**：MIB3 的成功容易造成"CarPlay 能控车"的错觉。真相是
**CarPlay 一直是投屏协议，MIB3 能控是因为车机在旁边另开了一扇门**。
ID7 有没有这扇门，这份文档答不了——只能实车探（路径 1、2）。

## 八、建议的下一步

按顺序，每一步都能明确回答一个"是/否"，不做无谓的猜测：

1. **实车跑一次路径 2（wlap5 端口扫描）** —— 半天内能出结论，不需要改代码。
   结论只有两种：白名单严格（放弃）或发现新端口（继续）。
2. **同时用 `main` 1.2.15 跑一次路径 1（EA 探测）** —— 看 `0xEA03` 有没有回。
   顺便验证我们那条 EA 链路在非奥迪车机上是否通用。
3. 前两步任一有正向信号，再谈下一步；两个都是否，**这个方向就到此为止**，
   把精力放回已经跑通的 MIB3。

**不建议**先做的：给 ID7 写任何控制代码、猜测 SOME/IP 服务 ID、反编译车机固件找"彩蛋"。
在没有确认入口存在之前，这些都是无底洞。
