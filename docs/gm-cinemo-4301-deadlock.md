# GM / Cinemo 车机（凯迪拉克）连不上：0x4301 死锁与修法

> 分析对象：`CarDeck-log-20261023-230404.txt`（CarDeck 0.1.13-debug，OnePlus PJZ110 / Android 17）  
> 车机：`CADILLAC_7731` / model `A2LL` / SA8155 / **Cinemo 组件栈** / manufacturer General Motors  
> 结论日期：2026-10-26。上游同族修复：shaonialife/cardeck **PR #19**（CT5，2026-10-23 合并）

## 1. 一句话结论

蓝牙 iAP2 这一层**全部打通**（识别、鉴权、问候、0x4300 都成功），卡在「车机一直不给热点凭据」：

- 车机能力清单里**没有 0x5702/0x5703**（旧协议 WiFi 配置交换），所以手机拿不到 SSID/密码；
- 车机声明会发 **0x4301**（新协议，AP 信息随它下发），但窗口内**一条都没发**；
- 而 0x4301 的发出前提是「车机在自己的 Wi-Fi 网段里发现手机的 `_carplay-ctrl._tcp` 并发邀请」——  
  手机没有凭据进不了车机网络，车机看不到手机就不发 0x4301，**双方互等**。
- 旧实现窗口一到就 `throw IOException` 拆链重连，每轮都把车机侧刚积累的状态清零，  
  于是变成「6 轮循环、车机始终静默」的稳定失败。

## 3. 为什么 0x4301 不来

`CinemoWIFIComponent` / `CinemoBTComponent` 这两个组件说明车机的 CarPlay 由 Cinemo 栈提供。  
同族车机（CT5/A2LL）的实测结论：

1. 真 iPhone 连的是车主热点（如「全新CT5」），并且**忘掉该网络后仍能无线连上** →  
   车机确实会经蓝牙把凭据推给手机，0x4301 会发，只是**晚发或等前置条件**；
2. 奥迪 MMI 9310 先例：Phase 1 结束后 **2 分 35 秒**才补发 0x4301；
3. 手动让手机先连上车机热点后重跑，旧版本仍失败——因为旧流程在拿到端点之前就拆链了，  
   根本没走到「在车机网络里广播 ctrl → 车机邀请 → 0x4301」这一段。

所以这是**时序/前置条件**问题，不是协议字段写错。

## 4. 修法（本分支 `bieke`，移植上游 PR #19）

`iap2/Iap2SenderSession.kt`

- 车机声明会发 0x4301、但窗口内未到时**不再抛异常拆链**：返回 `ssid=""` 的空端点，  
  链路进入保活；晚到的 0x4301 由 `pumpIncomingForever → handleLateStartSession →
  onEndpointUpdate` 重新触发完整配对。
- 空端点**不缓存空 wifi**：否则保活期 `parseStartSession` 的 `ap = wifi ?: fromSession`  
  会用空凭据覆盖晚到 0x4301 自带的 AP 信息，把唯一凭据来源丢掉。
- 车机**没声明**会发 0x4301（且无凭据）时，仍然抛异常——继续等只会空转。

`SessionController.kt`

- `onCarPlayEndpoint` 收到空端点 → 记日志、`phaseHint="等待车机下发连接信息（0x4301）…"`、  
  **不占 `sessionStarting`**（晚到端点要走「上一轮已结束」分支），转入等待观察。
- 新增 `watchForPendingStartSession`：每 5s 查一次手机当前 WiFi；  
  用户手动连上车机热点后弹「按车机热点继续 / 继续等待」，确认即用该 SSID 合成端点  
  重走 `onCarPlayEndpoint`（无端口 → mDNS/网关兜底，复用现成代码）；  
  同一 SSID 只问一次、换网络再问；`PENDING_START_SESSION_WAIT_MS = 5 分钟` 无进展才拆链。

## 5. 实车复测怎么判读

连车机后看日志（任一条出现即为进展）：

- `iap2 0x4301 窗口内未到但车机声明会发——不拆链，返回空端点进入保活` → 新行为生效；
- `>>> [..] 端点无 AP 信息（车机未在窗口内下发 0x4301）——…等待晚到 0x4301` → 进入等待态；
- `iap2 rx=0x4301 …`（保活期） → **晚发假设成立**，后面应自动入网出画面；
- `检测到已连接 XXX` 弹窗 → 手动入网路径可用，选「按车机热点继续」；
- `空端点等待 5 分钟超时` → 两种假设都不成立，需导出完整日志（等待期 Wi-Fi 状态、  
  是否有 ctrl 邀请 `GET /ctrl-int/1/connect`、mDNS 是否发现 `_airplay._tcp`）。

## 6. 仍未解决的部分

- *若车机的 0x4301 真的要求「手机已在它网络里」且**必须先有凭据才能入网**\*\*，  
  那就只能靠用户手动入网（车主在车机设置里能看到热点名/密码）——本分支已把这条路做成引导。*
- *手动入网后 mDNS 广播是否走在车机那个网络接口上，取决于 Android 的默认网络选择；  
  若日志显示已入网却 `mDNS 未发现 _airplay._tcp`，下一步要查 `bindProcessToNetwork` 与组播出口*。

## 7. 2026-10-26 实车复测（1.0.7 + 本分支）与两项改造

日志 `CarDeck-log-20261026-161325.txt`（一加 PJZ110 / Android 17，16:06 与 16:07 两次尝试）：

- 链路与协议全通：RFCOMM → `0x1d00/0x1d01`（CADILLAC_7731 / Cinemo BT+WIFI+HIDRemote）  
  → MFi `0xaa00/01(613B)/02(32B)/03(68B)/05` → `0x4e0d/0a/09/0b/0c` + `0x4300`（车机 ack=111）。
- **车机自始至终没发 0x4301**，两轮都按新逻辑进入保活，之后只有每秒一次的 `ff 55 02 00 ee 10`。  
  用户分别在 ~37s / ~19s 手动取消，**5 分钟窗口从未走完** → 「晚到」假设仍未验证。
- 等待期 `watchForPendingStartSession` 每 5s 轮询 `cmd wifi status`，全程拿不到 SSID →  
  没弹「检测到已连接」→ 手机当时 Wi-Fi 要么关、要么未连网。
- 另发现自动模式把该车机误杀：`16:06:19 跳过「CADILLAC_7731」（未发现 iAP2 服务）`，  
  而 13 秒后手动指定目标即连上。根因是 `awaitIap2Service()` 等不到 `ACTION_UUID` 广播  
  就当成「没有服务」。

本分支为此改了两处（1.0.8）：

1. **SDP 闸门改三态** `HAS / MISSING / UNKNOWN`：只有「收到广播且 uuids 里确实没有 …caff」  
   才算 MISSING；问不出结论（UNKNOWN）时先**不断音频**直连一次 …caff，探通即按车机处理，  
   探不通且不像个人音频设备才断开配置文件重试一次（奥迪那类「已连接时不开放窗口」的机型）。  
   顺带把 SDP 探测改成最多 2 次（首次常撞 `cancelDiscovery` 收尾）。
2. **等待期可观测**：进入等待时落一行说明（含「请保持 Wi-Fi 开启」）；之后每 30s 一行  
   `仍在等 0x4301（已等 Xs）· Wi-Fi=已关闭 / 已开但未连接 / "SSID"`；英雄卡副标题同步改成  
   「已连上车机，正在等它下发热点信息…」，不再显示「蓝牙 iAP2 握手」误导用户。

下次复测请：**先开手机 Wi-Fi**，点启动后**至少等满 2~3 分钟别取消**，同时看车机屏上有没有  
「CarPlay / 手机投屏」之类的确认项；日志里出现 `仍在等 0x4301 … Wi-Fi=` 那一行即可判断  
是「手机没进网」还是「车机就是不认」。

## 8. 「要不要发指令去引导 0x4301」的排查（2026-10-26）

### 8.1 从车机清单能推出什么

`0x1d01` 里车机声明它**会主动发** 11 条：`0xaa06 0x6800 0x6802 0x6803 0x4c00 0x4c02 0x4c03
0x4c05 0x5000 0x5002 0x4301`；**能收** 9 条：`0x6801 0x4c01 0x4c04 0x5001 0x4e09 0x4e0a
0x4e0b 0x4e0c 0x4300`。

实测它**一条都没主动发**（`0x6800` 没发 → 没有 HID；`0x5000` 没发 → 没有媒体订阅；  
`0x4c00` 没发 → 没有车况会话；`0x4301` 没发 → 没有 CarPlay），只对我们的包回 ACK。  
这种「只应答、不发起」的形态，指向「它在等某个前置消息」，而不是「它不会发」。

### 8.2 我们能发的只有清单里的 9 条

车机不收的消息发出去也没用，所以「引导」只能落在这些上。其中与 CarPlay 启动相关的只有  
`0x4300`（可用性）与 `0x4e0e`（传输标识）。检查代码发现一处可能顺序错位：

- 真 iPhone 在 `0x4300` 前后就会给 `0x4E0E`，告诉车机「这条会话挂在蓝牙上」；
- 我们此前把 `0x4E0E` 放在**等待窗口过期之后**才补发（本日志 `16:06:43.253`，  
  即 `0x4300` 之后 8 秒），如果车机正是等它，那 8 秒里它看到的是「一台没说清传输方式的设备」。

### 8.3 本版加的「催问」机制

进入空端点等待后，保活泵每 **15 秒**重发一次 `0x4e0e` + `0x4300`，最多 20 次（5 分钟），  
首次与每第 4 次落日志：

```
iap2 催问第 1 次：重发 0x4e0e + 0x4300（车机仍未下发 0x4301，链路正常保活中）
iap2 催问共 N 次后收到可用 0x4301——停止催问        ← 若催出来了
```

这是**假设验证**，不是已证实的协议要求。复测只看三件事：

| 日志                     | 结论                                                         |
| ---------------------- | ---------------------------------------------------------- |
| 催问若干次后出现 `rx=0x4301`   | 「等前置消息」成立——下一步把 `0x4e0e` 前移到 `0x4300` 之前                   |
| 催满 20 次仍无 `0x4301`     | 发消息引导这条路不通，问题在车机侧条件（屏幕确认 / 手机 Wi-Fi 未入网 / 该机型不支持非 MFi 发送端） |
| `0x4301` 在首轮 8 秒窗口内就来了 | 与催问无关，属随机时序，需再看首轮日志                                        |

## 9. 参考上游 PR #10 / #17 后的比对与移植（2026-10-26）

### 9.1 PR #10（BMW iD9，新代协议）——已全部在本仓库，无需再移

本项目当时已实现 PR #10 的处理，包括 `0x1D01` 能力清单分派（`accessoryReceiveIds`
+ `receiveListDeclared`）、`0x5703` 改 `expectOrNull`、新协议 8s 窗口、`parseStartSession`
接受 `wifi=null`、`BinaryPlist` 无符号长度 / `parseRecovered` 裁尾 / `0x3 日期` / `0x7 UTF-8`
/ `0xB UUID` / UID 长度按 `info+1`、`/info` 诊断 + `scheduleSideProbe` + `uuidText`、
`forceKeyFrame` 立即编 I 帧。

**对本案没有帮助**：iD9 收到 `0x4300` 后**立即**回 `0x4301`（8s 窗口绰绰有余），
它证明的是「新协议本身可行」，不能解释凯迪拉克为何一条都不发。

### 9.2 PR #17（BMW iD8.5）——三处值得移植，已移

| 移植项 | 原问题 | 本仓库改法 |
|---|---|---|
| 设备状态问候紧跟 `0xAA05` | 车机据这批消息判定发送端就绪，晚发会被当成没起来。本仓库原本排在 `awaitOptionalHid`（最多 2s）之后——凯迪拉克日志里 `0xaa05` 在 33.248、问候在 35.249，中间正好空了 2 秒 | 抽出 `sendDeviceStateGreetings(force)`，在 `0xAA05` 之后立刻发；后面原位改成幂等空转 |
| `0xEA00` 的 param 1 用协议名 | 发协议号时车机不回 `0xEA03` | `Iap2Csm.string(1, name)` |
| 车机不推进时重发问候（「救援」） | iD8.5 用「重发问候 + 重发 0x5702」把 `0x5703` 救出来 | 并入本分支的催问：每次催问先 `sendDeviceStateGreetings(force=true)`，再 `0x4e0e`、`0x4300` |

### 9.3 与本案的关系

第 3 项是**唯一能直接作用于「车机不发起」这个症状**的：凯迪拉克声明 11 条却一条不发，
和 iD8.5 上「`0x5703` 迟迟不回、重发问候后就回了」是同一类现象——车机在等发送端
把自己「报全」。若这次复测催问后 `0x4301` 到了，就说明问候/传输标识这套自报信息
此前根本没被车机消化（因为晚于 `awaitOptionalHid` 发）。
