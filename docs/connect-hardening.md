# 连接健壮性：失败定性、候选地址、阶段预算、多屏选择

本文记录 1.2.9 对「连接过程」做的四处加固，以及每处的**判定依据与已知边界**。
四条改动都来自现场日志，不是设计推演；也没有一条改变协议行为。

## 0. 起因

| 日志 | 现象 | 真实原因 |
| --- | --- | --- |
| 2026-10-30 `221747` | 有画面、一直没声音，随后断链 | 车机对 `pair-setup` / `pair-verify` 都回 `{Error:2, State:4}`；我们**把拒绝读成成功**，派生出对不上的密钥 → 加密 SETUP 被静默丢弃 10s → 降级明文会话（无共享密钥 → 音频/触摸整条跳过） |
| 2026-11-01 `090105` | 连接等 29.7s，音频等 88s | 连接慢是车机回连 14.9s + WiFi 入网 7.7s + `/info` 慢应答 3.3s 叠加；音频慢是 WiFi 入网把引擎重启（已在 1.2.8 用音频看门狗解决） |
| 同上 | 「为什么这次连接花了多久」只能人工掐表 | 七个阶段的耗时散落在各自日志里，没有汇总 |

## 1. 终止性失败分类（①）

### 错在哪

配对应答里的 `TYPE_ERROR`（TLV `0x07`）从 1.0 起一直被丢掉：

- `pair-setup` M4 回 `{Error:2, State:4}` → 代码只找 `TYPE_PROOF`，报「M4 缺少 proof」，真实原因从未进日志；
- `pair-verify` M4 回同样的内容 → 代码只判 `State == 4`（正常完成标记）→ **假成功**。

两者叠加的后果就是 221747：整条音频链路被跳过，而日志给出的两条原因（「加密 SETUP 被拒（403）」、「弹窗里没勾声音」）都是假线索。

### 现在的规则

`PairingClients` 的每个应答**先看 Error，再看 State**，抛 `PairingRejectedException(stage, code, rawCode, state)`。
`PairingPolicy` 把「阶段 + 错误码」翻译成处置：

| 错误码 | 含义 | 处置 | 为什么 |
| --- | --- | --- | --- |
| `0x02` AUTHENTICATION | 车机不认这台手机的配对身份 | **确定性**；`pair-setup` 段先改走已配对快路径（pair-verify） | 车机很可能已存了我们的公钥，只是不接受再注册一次（与 403 同义） |
| `0x04` MAX_PEERS | 车机保存的设备已满 | **确定性**，立刻停 | 用户不去车机删设备，重试永远是同一个码 |
| `0x05` MAX_TRIES | 尝试次数用尽 | **确定性**，立刻停 | 只有车机自己的计时器能解除 |
| `0x03` BACKOFF / `0x07` BUSY / `0x06` UNAVAILABLE | 暂时状态 | 可重试（BACKOFF 停 5s，其余 1s） | 车机重开 AirPlay 窗口时状态就是抖的 |
| 规范外私有码 / 无码 | 未知 | 可重试 | 宁可多试一次，也不要把能连的车机判死 |

被判定为确定性拒绝时，**明文会话仍然继续**（画面不需要共享密钥），但会当场写一行：

```
AIRPLAY: ⚠ 本会话无共享密钥（车机拒绝配对）：画面正常，音频与触摸不可用。要恢复声音需在车机侧删掉本机的配对记录后重连
```

### 短期记忆（省掉 120s 白等）

车机确定性拒绝时，旧行为仍会在 120s 配对窗口里每 2s 重试一次，全部得到同一个错误码。
`PairingMemory` 按接收端（`pk` → `deviceid` → `SSID`）记一条，15 分钟内直接跳过 `pair-setup`。

三条自我纠正保证它不会误伤本来能连的车机：

1. 15 分钟 TTL，过期自动失效；
2. 只跳过 `pair-setup`，不跳过明文 SETUP；明文 SETUP 若被拒，`retryWithPairing` 仍会补做一次配对；
3. 任何一次配对成功（含补配对成功）立刻清除记忆。

> 记忆键**不用 IP**：车机热点每轮可能换地址，用地址当键要么永远命中不了、要么命中到别的设备。

## 2. 候选地址与身份解耦（②）

事实（同生态实现的现场记录）：**mDNS 通告的地址与 0x4301 自报的地址可能既不同族也不同值**——一台 DiPlay 的 `0x4301` 报 IPv6 link-local，mDNS 通告 IPv4 `192.168.43.1`。

结论：地址只是**连接候选**，身份判定必须靠 `pair-verify` 的 pk 签名。本项目的代码本来就是这个结构（`ensureConnected` 按 IPv4 → 全局 IPv6 → 链路本地 IPv6 逐个试），1.2.9 补的是两件「看不出来」的事：

- 配对开始打一行完整候选：`AIRPLAY: 连接候选 192.168.43.1（IPv4）、fe80::1%wlan0（链路本地 IPv6）（身份判定只看 pk，与地址无关）`；
- pk 签名不匹配时**不再只是一句 `=false`**，而是显式告警并指出风险（可能是 TXT 里的 pk 过期，也可能连到了同网段的另一台 AirPlay 设备）。**仍然不中断**——部分自制接收端的 pk 本身就是空壳，硬失败会把能用的车机挡在门外。

## 3. 阶段预算与首帧门（③）

`util/ConnectBudget` 在每轮连接开始计时，进阶段打一行、结束打汇总：

```
STAGE: 本轮开始（0x4301）——预算：等端点 5min / 热点 60s / 配对 120s / SETUP 30s / 首帧 20s
STAGE: 加入车机热点开始（上段 等车机连接信息（0x4301） 用时 8.2s，本轮累计 8.2s）
STAGE: AirPlay 配对开始（上段 加入车机热点 用时 3.1s，本轮累计 11.3s）
STAGE: 会话建立（SETUP）开始（上段 AirPlay 配对 用时 120.4s，**超预算**，本轮累计 131.7s）
STAGE: ✓ 首帧已到达，开始推流（本轮累计 23.5s）
STAGE: 本轮小结（0x4301）共 23.5s：等车机连接信息（0x4301） 8.2s → 加入车机热点 3.1s → AirPlay 配对 12.2s → 会话建立（SETUP） 0.0s → 等首帧 0.0s
```

预算值**全部沿用已有常量**，不引入第二套超时：

| 阶段 | 预算 | 来源 |
| --- | --- | --- |
| 等端点 | 5 min | `PENDING_START_SESSION_WAIT_MS`（奥迪 MMI 9310 实测 0x4301 晚到 2 分 35 秒） |
| 加入热点 | 60s | `CAR_WIFI_BIND_WAIT_MS`（45s）取整 |
| 配对 | 120s | `PAIRING_WINDOW_MILLIS` |
| SETUP | 30s | `INITIAL_SETUP_WINDOW_MS` |
| 首帧 | 20s | 新增：会话已建立，20s 出不来帧就不是「慢」而是「没有」 |

### 首帧门只报告，不拆链

`startFirstFrameGate()` 在 SETUP 成功后等首帧，20s 没帧就打：

```
STAGE: ⚠ 等首帧超时（20s 内没收到任何视频帧）——画面来自本机 CarLife+：确认它处于「无线连接」且引擎在推流（7240）；会话本身已建立，不需要重连车机
```

**故意不拆链**：拆链由视频看门狗与冻结恢复负责，再叠一套超时就是两套语义互相打架（这台项目历史上反复踩过）。
这里要解决的只是「日志在 SETUP 成功之后就断片」——事后无从判断是黑屏还是 CarLife 没在投。

## 4. 多屏选择（⑤）

旧实现固定取 `displays[0]`（准确说：第一块宽高可解析的屏）。多屏车机（大连屏 / 仪表）若先声明副屏，画面就推到那块屏上，比例与触摸坐标全错，日志还看不出选错了。

现在的规则（`CarDisplayGeometry.select`）：

1. **车机没声明 `type` → 取第一块有效屏**（与旧行为完全一致，绝大多数车机走这条）；
2. 声明了 `type` 时：`type == 0` 优先 → 其余 `type` 升序 → 面积大优先 → `maxFPS` 高优先 → 声明下标兜底（保证同样输入永远同样输出）。

同时修正两个字段的来源：`displayUuid` 与 `maxFps` 改取**选中那块屏**的值，不再固定读 `displays[0]`。

多屏时必打一行：

```
AIRPLAY: /info 共 2 块屏候选：displays[0] 800×480 type=1；displays[1] 1920×720 type=0 maxFPS=60 → 选中 displays[1]
```

> ⚠ 这条排序是**假设**，不是实车结论：目前没有一台多屏车机接入过。所以它只在车机自己声明 `type` 时生效，并且一定会把候选与选择结果写进日志——实车一跑就能验证。

## 5. 明确不做的事

| 不借鉴 | 理由 |
| --- | --- |
| 帧率兜底压到 15fps | 我们是**转发** CarLife 已编好的码流，压 15 只会让画面卡死；目标帧率仍是「车机报了跟随、没报按 60」 |
| 按编码器能力筛屏 | 我们没有编码器这个部件（码流由 CarLife 引擎产生），无从判断 AVC surface 能不能扛 |
| listener 与拨号竞速 | 会取代「用户选车机发起还是手机拨号」这个二选一，但 B233 实车明确「拆 HFP 会坏窗口、拨号要隔 15 秒」，直接竞速可能打断车机入网窗口，必须实车验证后再做 |
| 证书链 / attestation 严格校验 | 我们求的是「这台车出画面」，且保留明文会话作为兜底；pk 不匹配只告警不中断 |

| 想知道 | 搜这行 |
| --- | --- |
| 这次连接一共多久、慢在哪 | `STAGE: 本轮小结` |

| 画面为什么没出来 | `STAGE: ⚠ 等首帧超时` |
