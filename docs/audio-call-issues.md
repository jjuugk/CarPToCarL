# 音频握手与来电黑屏：真机日志分析（2026-10-26）

两份现象、三份导出日志（`CarDeck-log-20261026-100321 / 102215 / 103416`，App 1.0.3，
荣耀 PTP-AN10 + 奥迪 MIB3）。本文只写**日志能证明的**，推断处会标注。

## 一、时间线（同一次会话，10:02:18 起）

| 时刻 | 事件 | 含义 |
|---|---|---|
| 10:02:36.068 | `AIRPLAY: ✓ 音频流协商成功 … dataPort=6000 controlPort=6011` | 音频通道协商完成 |
| 10:02:36.691 | `AUDIO: 同步包已启用 → 10.174.189.1:6011` | 开始每秒发同步包 |
| 10:02:36.692 | `AUDIO: 首个同步包已发出（X 位=1）` | 只发出这一个 |
| **10:02:37.693** | **`AUDIO: 同步包发送停止 - sendto failed: ECONNREFUSED`** | **同步线程直接退出** |
| 10:03:16.270 | `CARLIFE: 媒体 音频格式宣告 44100Hz` + `0x30002 音频包` | 引擎第一次开音频 |
| 10:03:16.281 | `AUDIO: 首帧 557B` | 连接后 **40 秒**才有第一包 PCM |
| 10:21:13.698 | `0x30003 音频包（长度 0）` + 车机 `changeModes` | 引擎音频停（来电） |
| 10:21:14 → 10:21:52 | 视频 0.8 fps、音频报告消失、NSD 服务消失又重现 | 画面源停摆 37 秒 → 车机黑屏 |
| 10:24:19.107 | `0x30002 音频包` | 引擎音频恢复——比画面恢复晚了 **2.5 分钟** |
| 10:31:07 → 10:31:47 | 视频再次停摆 39.6 秒 | 第二次来电 |
| 10:31:50.981 | `0x30003` | 音频再次停止，直到日志结束（10:33:59）没再恢复 |

## 二、结论 1：同步包「发一次就死」（代码缺陷，已修）

`AudioSender.startSyncLoop()` 原来是这样：

```kotlin
try {
    while (running.get() && !client.isClosed) { … client.send(…) … }
} catch (error: Exception) {
    log("AUDIO: 同步包发送停止 - ${error.message}")   // ← 线程到此结束
}
```

连接式 UDP 的 `ECONNREFUSED` 是**一次性的 ICMP 端口不可达**，只要继续发就还能成功；
但旧实现把它当成致命错误。后果：整场会话只在 36.692 发出过**一个**同步包，
RTP↔NTP 锚点等于没有（第二次会话 10:25:01.501 同样一次就死）。

为什么第一次会 `ECONNREFUSED`：车机在 `SETUP` 应答里给了 `controlPort=6011`，但那一刻
它还没在该端口上监听（音频流是「会话 RECORD 之后追加」的，SDP 里只有视频流）。
这是**时序竞争**，不是配置错——重试就能过去。

> 与「刚连上没声音」的关系：锚点缺失时车机只能按到达时刻猜排播，启动初期最容易静音。
> 这一点日志无法单独证明因果，但「锚点从第一秒就没了」是事实。

## 三、结论 2：首包 PCM 晚 40 秒（引擎侧行为）

10:02:36 音频通道就绪，但直到 10:03:16 引擎才发 `0x30001`（格式宣告）+ `0x30002` + 首包 PCM。
即 **CarLife 引擎在「有媒体真正开始播」之前不推 PCM**，导航播报本身不一定能触发它。
这不是 App 能凭空补出来的音频——App 侧只能保证「引擎一出声，车机马上能播」。

排查时值得先确认的一条：`CarLifeAudioSink.setPlaybackPaused()` 会按媒体会话状态丢 PCM
（历史修复：引擎暂停后仍推残留 PCM → 重复播放）。**这条判定原来没有时限**——连上车机时
手机里常驻一条「暂停」的音乐会话（很常见），导航播报、提示音就会被长期当成残留丢掉，
症状恰好是「开导航没声音、放音乐才有声」。1.0.4 改成**只在暂停后 15 秒内截断**，
并给这条路径加了丢弃计数日志，下次日志可一眼确认。

## 四、结论 3：来电期间是**源停摆**，不是链路问题

- 视频：37 秒内只有 4 帧/5 秒的心跳帧、**零个新 IDR**；
- 音频：`0x30003` 之后引擎 PCM 归零（5 秒 0 包）；
- 链路活着：keepAlive、timesync、feedback、控制通道 tx 全程正常，只有 NSD 抖动过一次。

所以黑屏**不是** AirPlay 掉链，而是手机侧画面源没有内容可编——通话界面属于系统安全窗口，
录屏/截取拿不到（Android 对 `FLAG_SECURE` 的限制），引擎只能给黑帧或干脆不出帧。

## 五、结论 4：挂断后「无声音」= 引擎没恢复音频

画面在 10:21:52 就恢复了，音频直到 10:24:19 才收到 `0x30002`——中间 2.5 分钟车机侧全静音，
这正是用户说的「挂断后无声音」。App 侧此时并没有停发，是**没有数据可发**。

## 六、1.0.4 的改动

| 改动 | 文件 | 目的 |
|---|---|---|
| 同步包失败不再终止线程：持续每秒重试，失败满 10 次重开套接字 | `audio/AudioSender.kt` | 锚点从「一次就死」变成「一直有」 |
| 新增 `resyncAnchor(reason)`：补发 3 个同步包 | 同上 | 音频中断后恢复时立刻重新对齐车机时钟 |

| 引擎音频恢复时自动 `resyncAnchor` | `carlife/CarLifeHijack.kt` | 缩短「有数据了但车机还没对齐」的空窗 |
| 画面源停摆看门狗：8 秒无帧记一条，恢复时记停摆时长 | 同上 | 下次能直接区分「源没画面」与「车机解码问题」 |

## 1.0.6 的改动

`SessionController.rebuildAudioChannel()`：通话结束后 **2.5 秒**重建一整条音频流
（新的 `streamConnectionID` / 新 dataPort·controlPort / 新编码器 / 新同步锚点），
并补发 `RECORD` 把新流纳入已激活的会话。

- 等价于「重连一次就好了」在音频层的动作，但**不动视频**（视频是另一条流）；
- 顺序是「**先协商新的、成功了才停旧的**」：SETUP 被拒时旧流继续推，
  不会把「本来还有声」搞成「彻底没声」；
- 日志会出 `AUDIO: 音频流重建完成（新 dataPort=… controlPort=…）`，
  失败则出 `重建协商失败——保持原音频流继续推`。

# 追加：真正的「导航没声音」根因（2026-10-27，1.0.13）

前文把「开导航没声音」归因到暂停窗口误丢 PCM。**那不是全部**。1.0.13 之前的日志
（`files/main_debug.log`，WinPlay 测试台，10:34:27–10:35:19）给出了直接证据：

```
[10:35:14.033] CARLIFE: 0x40002 音频包（长度 0，暂不处理）
[10:35:14.042] CARLIFE: 0x40003 音频包（长度 1280，暂不处理）   ← 导航播报 PCM，被丢弃
[10:35:14.042] CARLIFE: 0x40001 音频包（长度 7，暂不处理）
```

## 一、根因：导航走的是 TTS 通道（9241），不是媒体通道（9240）

CarLife 有**两条音频流**：

| 通道 | 端口 | 包类型 | 内容 | 旧实现 |
|---|---|---|---|---|
| 媒体 | 9240 | `0x30001/0x30002/0x30003/0x30006` | 音乐 | 正常转发（`onAudioPcm`） |
| **TTS** | **9241** | **`0x4xxxx`** | **导航播报、语音提示** | **全部落进 `else` →「暂不处理」→ 丢弃** |

`CarLifeHuClient.audioReader()` 的 `when(type)` 只列了媒体的四个常量，TTS 通道虽然
连上了（`audioReader(tts.getInputStream(), "TTS")`），但所有 `0x4xxxx` 包都走 else 丢弃。
所以**放音乐有声、开导航没声**——两条流根本不在同一条路上。

第二层原因：媒体 sink 的「音乐会话暂停 → 丢弃残留 PCM」联动也在这台机器上触发了
（`10:35:04.338 CARLIFE: 音乐会话暂停——丢弃引擎残留 PCM`），而导航播报恰恰发生在
音乐暂停的时候。TTS 必须**不参与**这条联动。

## 二、1.0.13 的改动

1. `CarLifeProtocol`：新增 `TTS_PKG_INIT=0x40001`、`TTS_DEFAULT_RATE=16000`。
   注意**不照搬媒体编号**——实测 TTS 的数据包在 `0x40003`（媒体是 `0x30006`），
   编号体系不同，所以只认两条铁律：**有负载 = PCM，长度 0 = 开停信号**。
2. `CarLifeHuClient.audioReader(..., isTts)`：TTS 通道单独解析
   - `0x40001` → `parseAudioInit` 取采样率/声道（与媒体通道同一个解析器）
   - 任何 `length > 0` → `onTtsPcm(payload)`（**首包会打印一条 ✓ 日志**）
   - `length == 0` → 只记开停，不丢数据
3. `CarLifeAudioSink(log, dropWhenPaused)`：TTS sink 传 `false`，不参与暂停丢弃。
4. `CarLifeHijack`：媒体 sink 与 TTS sink **各自一套**（采样率/声道独立：
   媒体 48k 立体声，导航常是 16k 单声道），共用一个 `AudioSender`。
5. `AudioSender.feedPcm` 加 `@Synchronized`：接入 TTS 后有两路线程同时写
   `passthroughBuffer`（非线程安全），不加锁会半帧交错 → 爆音。

## 三、复测时确认这三行

1. `CARLIFE: TTS 音频格式宣告 16000Hz 1ch（导航播报通道）` —— 格式认到了
2. `CARLIFE: ✓ 收到导航播报音频（TTS 首包 1280B，16000Hz 1ch）` —— 数据进来了
3. `CARLIFE: 音频直通 … · 电平 xx%（非零 xx%）` —— 电平非 0 才说明真的是声音

如果第 2 行有、车上仍没声，那问题就落到 AirPlay 侧（音频 SETUP/音量/车机排播），
按前文「复测判读」的三行继续查。

# 通话音频通道适配（2026-10-29）

前几节解的都是「通话**之后**媒体音频不回来」。这一节处理的是通话**期间**：
把接收端的输出通路从媒体档切到 `audioType=telephony` 档。

## 一、为什么必须换流，不能调参数

`audioType` 只在 SETUP 里出现一次，一条流建成后无法中途改变语义。车机把
`media` 与 `telephony` 当成**两台不同的输出设备**：只有收到 telephony 档的流，
它才会打开通话增益与麦克风通路。这就是「通话在车机上永远没声音」的结构性原因——
媒体流一直占着媒体通路，通话通路从来没被打开过。

改动（`SessionController.switchAudioScene`）：

```
AudioManager.mode 进入 IN_CALL / IN_COMMUNICATION / RINGTONE
  → 换流：媒体档 → telephony 档（先建新的、成功后停旧的、补 RECORD）
  → 转发 0x4155 CallStateUpdate（此时通话流已经在线）
退出通话 → 换回媒体档（等价于「新建一条流」，接收端会重新打开输出设备）
```

音源不变：还是 CarLife 引擎的 PCM（`CarLifeAudioSink` 取的是
`SessionController.audioSender`，换字段即生效），只是接收端换了通路。

## 二、Android 侧的硬限制（决定了能做到哪一步）

普通 App **拿不到通话双方的音频**，这条没有绕法：

| 手段 | 结论 |
|---|---|
| `AudioPlaybackCapture` | 只允许 `USAGE_MEDIA / USAGE_GAME / USAGE_UNKNOWN`；通话是 `USAGE_VOICE_COMMUNICATION`，抛异常 |
| `AudioRecord` + `VOICE_CALL/VOICE_DOWNLINK` | 需要 `CAPTURE_AUDIO_OUTPUT`（系统签名权限） |
| `setCommunicationDevice` | 只能在已有设备里选，不能造设备、更不能接管别人的通话 |

所以本次做的是**协议与通路**：车机会认到通话场景、把音频路由让给 telephony 档；
但「车机喇叭里出对方的声音」在没有 root 的前提下做不到（想做成必须
`VOICE_CALL` 采集或 LSPosed hook 系统电话）。

## 三、验证要看这几行

1. `AIRPLAY: 通话类档 type=… audioType=telephony output=0x… input=0x…`
   —— 车机到底有没有声明通话档。**没有声明就到此为止**，任何代码都补不出来。
2. `AUDIO: 进入通话（IN_CALL）→ 换到通话音频档`
3. `AUDIO: 音频流已切到 t100/telephony/0x…` —— 切上了；否则会跟一行
   `车机未声明通话音频档（telephony），保持媒体流`
4. `IAPLINK: 主动补推 0x4155（通话状态=3）`
5. 挂断后 `AUDIO: 音频流已切到 … media …` —— 切回媒体档

## 四、有意没做的两件事

1. **麦克风上行流（`input=true`）没有真建**。`microphoneCandidates()` 只生成候选并
   打进日志（`AUDIO: 麦克风上行能力=…`）：上行要用我们自己的 UDP 监听端口换车机推流，
   端口与密钥派生方向都与下行不同，没有车机日志无法确认方向，硬写只会多占一次
   接收端资源仲裁。等日志证明车机声明了 PCM 输入位再做。
2. **通话档拆链不归因媒体档**：`attributeAudioTeardown` 在 `audioInCallMode` 时直接
   跳过，否则一次通话档不兼容会把好好的媒体档记进「踩雷名单」。
