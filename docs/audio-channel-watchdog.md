# 音频通道看门狗（9240 / 9241）

> 起因：2026-11-01 日志 `CarPToCarL-log-20261101-090105.txt`——
> 「等一会才连接上车机，播放音乐也要等一段时间才出音频」。1.2.8 修。

## 一、现象与日志证据

同一次连接里，画面 8 秒就出来了，声音却要等 **88 秒**。日志时间线（已删无关行）：

```
08:57:38.188  CarPToCarL 1.2.6 就绪
08:57:38.995  CARLIFE: 媒体 音频通道断开 - Connection reset      ← 9240 死了
08:58:00.499  CARLIFE: TTS 音频通道断开 - Connection reset       ← 9241 也死了
08:58:0x      （视频看门狗重连 8240 → 画面恢复，车机上看得见）
09:00:22.842  CARLIFE: 媒体 音频格式宣告 44100Hz 2ch 16bit        ← 88 秒后才有声
```

`Connection reset` 的来源是荣耀 CarLife 引擎被重启（这次是 WiFi 入网触发）。
视频链路活下来，是因为它**本来就有一条看门狗**（`videoSupervisor`，每秒检查
socket 是否还活着，死了就重连 8240 并重发 `98311`）。

音频链路当时**一条看门狗都没有**：`audioReader()` 读到异常 → 打一行日志 → 结束。
socket 已经关了，`sockets[9240]` 却还挂在 map 里，没有任何代码会去重建它。
声音靠的是引擎下一次自己复位推流——所以它「自己好了」，但代价是 88 秒。

## 二、改法：两条互斥路径，与视频看门狗同构

在 `CarLifeHuClient` 里新增 `audioSupervisor()`（线程名 `carlife-audio-dog`，1 秒一轮），
媒体（9240）与 TTS（9241）各用一个 `AudioChannel` 记录状态。

### 路径 A：socket 真的死了 → 立刻重连（本版主项）

判据：`sockets[port] == null || socket.isClosed || channel.dead`。

`channel.dead` 由读线程的 `finally` 置位。这里有一个坑：`reopenAudio()` 会
`close()` 旧 socket，旧读线程随即走 `finally`，若无条件置死就会把**刚接上的新通道**
判死，形成「重连 → 秒判死 → 再重连」的死循环。所以每次挂读线程都递增
`channel.generation`，读线程只在自己这一代仍是最新时才允许置死。

重连不设次数上限（引擎冷启动期可能连续 reset），超过 3 次后每次多停 2 秒，
避免把引擎打满——和视频看门狗的处理一致。

### 路径 B：socket 活着但不出声 → 重连一次（带三重设限）

判据（全部满足才动手）：

| 条件 | 值 | 为什么 |
| --- | --- | --- |
| 连续无 PCM | ≥ 20 秒 | 音乐的自然停顿不会这么久 |
| 距离通道建立 | ≥ 20 秒 | 刚接上要给引擎一点推流时间 |
| 视频仍在出帧 | 3 秒内有帧 | 引擎活着，问题只在这条音频流上；视频也停了是会话层的事，别跟着乱重连 |
| 确实该有声 | 引擎恢复播放（`0x30004`）且未发 `0x30002`/`0x30003`，**或** 媒体播放周期活跃 | 否则「人只是停在桌面没开音乐」也会被当成故障 |
| 未超次数 | 最多 3 次 | 之后停止重试并留一条日志 |

退避：第 n 次重连后等 n×20 秒才允许下一次（20 / 40 / 60）。收到任何一包 PCM 即清零，
并打一条「音频通道恢复（断流 xx 秒，重连 n 次后恢复）」。

三重设限不是保守，是必要：默认屏幕上没有声音在放是**常态**，只按「静默」判会
在每个停车等待的间隙反复重连，把引擎的音频管道打断——比不修更糟。

### TTS 只走路径 A

9241 上没有导航播报时本来就该长时间静默，按沉默判会天天误重连；
但它的 socket 一样会随引擎重启而死，所以断链重连必须有。

## 三、两个必须保留的细节

1. **格式宣告状态要跨重连保留**（`channel.announced` / `channel.rate`）。
   原来它是 `audioReader()` 的局部变量，重连后新读线程会以为「引擎没宣告过格式」，
   给上层报一个 48kHz 立体声兜底值，把真实的 44.1kHz 覆盖掉——声音会变调。
2. **重连不动上层 sink**。`CarLifeAudioSink` 在 `CarLifeHijack.workerLoop()` 里创建，
   音频重连只换 socket 与读线程，sink 与 `AudioSender` 保持不动，所以车机侧的
   RTP 流不会中断。

## 四、日志关键字

排查时按这几行看：

```
CARLIFE: 媒体 音频通道断开 - Connection reset（看门狗会自动重连）   # 检测
CARLIFE: 媒体 音频通道已重连（第 1 次断链重连）                     # 路径 A 生效
CARLIFE: 媒体 音频通道 25 秒零 PCM（画面正在正常出帧）——重连 9240（第 1/3 次，20 秒后才会再试）
CARLIFE: 媒体 音频通道恢复（断流 25 秒，重连 1 次后恢复）           # 闭环
CARLIFE: 媒体 音频通道连续 3 次重连仍无 PCM——停止重试（等引擎自己恢复；仍无声可重开 CarLife+ 的「无线连接」）
```

最后一条出现说明引擎侧已经不推流了，此时该做的是重开 CarLife+ 的「无线连接」，
而不是继续重连——所以看门狗停在这里，把判断权交回给人。

## 五、不做什么

- **不自动拉起 CarLife 引擎**：`workerLoop()` 里早有结论，自动拉起只能拿到欢迎页，
  拿不到荣耀的画面源（见该处注释）。
- **不重建整个 CarLife 会话**：视频/音频共用控制通道（7240）的握手状态，
  为了一条数据流重走一遍 15 秒版本协商，代价远大于收益。
- **不把「静音 PCM」当异常**：引擎推过来的全是零值样本是合法状态（音乐 App 在放
  但被静音），看门狗只看「有没有包」，不看电平。
