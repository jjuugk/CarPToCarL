# 别克 E2LB（BUICK_3799）0x4300 之后车机停止 ACK —— 2026-10-26 20:29 日志分析

日志：`CarDeck-log-20261026-203321.txt`（1.0.8 / bieke 分支 `8d1650c`）
车辆：`BUICK_3799` · model `E2LB` · manufacturer `Saic General Motors`
手机：一加 Ace 5 Pro（PKR110，Android 17），本机蓝牙 MAC `4C:92:D2:BB:8D:04`

## 1. 结论先说

1. **链路、MFi、识别全部通过，卡点与凯迪拉克完全同源**：车机在 `0x1D01` 里声明了
   11 条「我会发」的消息（含 `0x6800` StartHID、`0x4301` StartSession），实际**一条都没发**。
2. **这台车的症状比凯迪拉克更严重一步**：凯迪拉克对 `0x4300` 是「ACK 但不推进」，
   这台是**收到 `0x4300` 后整个控制会话停止 ACK**——连纯 ACK 都不回了，只剩每秒一次的
   `ff 55 02 00 ee 10` 链路心跳。23 秒后我方重传看门狗判定 `packet 111 not acknowledged`
   拆链，于是形成 **~42 秒一轮**的「连上 → 协商完 → 车机沉默 → 拆链 → 重连」死循环，
   5 轮一模一样，5 分钟内一次 `0x4301` 都没等到。
3. **两张车的 `0x4300` 字节完全相同**（除 MAC 外逐字节一致，见 §4），凯迪拉克 ACK、
   别克不 ACK ⇒ **报文体本身在这台固件上不被接受**，而不是我们发错了帧结构。
4. 「按车机声明裁剪可选消息」这项改动**确实生效**（`0x4e0d`/`0x4e0e` 都被跳过），
   但它**没有换来车机推进**——说明「喂了它没声明要的帧」不是这台车不干活的原因。

## 3. 为什么判断是「0x4300 打住了它」

- 时间点精确吻合：最后一个 ACK 是 `0x4e0c`（seq 109），下一个我们发的帧就是 `0x4300`（seq 110），
  从此引擎再也不产生任何 `LINK rx`。
- **RFCOMM 没断**：期间车机持续发 `ff 55 02 00 ee 10`（每秒一次，链路层心跳），
  说明蓝牙连接活着、只是控制会话不干活了。
- **同样的字节在凯迪拉克上正常**：见 §4，除 MAC 外逐字节一致，凯迪拉克回 `ack=111` 并稳定保活到用户手动取消。

差分对比（同一构建的 1.0.7/1.0.8 两个日志）：

| | 凯迪拉克 CADILLAC_7731（1.0.7） | 别克 E2LB（1.0.8） |
|---|---|---|
| `0x4300` 报文体 | 新版嵌套体 | **完全相同** |
| 车机对 `0x4300` | `ack=111` ✓ | **零 ACK** ✗ |
| 链路存活 | 直到用户取消（>45s） | 23s 后被重传看门狗拆掉 |
| 0x6800 / 0x4301 | 声明但都不发 | 声明但都不发 |

## 5. 已发现的两个自身 bug（与车机无关，已在本轮修掉）

1. **保活观察者叠加**：每次断链重连都新起一个 `watchForPendingStartSession`，旧的只认
   `connectCancelled` 不退出 → 5 轮后同时有 5 个观察者在跑，日志里出现
   「已等 30s / 61s / 91s / 122s / 153s」并存的假象（同一时刻 5 个不同起点）。
2. **5 分钟预算每轮重置**：观察者的 deadline 从**本轮会话**算起，车机 42 秒断一次链
   就永远走不到超时 → 界面上写的「最多 5 分钟」是假的，实际会无限空转。

## 6. 本轮改法（bieke）

### 6.1 `0x4300` 报文体三档阶梯（`AvailabilityBodyMemory`）

参考实现（CarWith-CarPlay）为此准备了两套报文体，且「23 款及以前」档**根本不发 `0x4300`**。
我们无法离线判断哪台车吃哪种，于是改成「一次连接试一种」，判据用「对端是否还回链路 ACK」：

| 档 | 报文体 | 来源 |
|---|---|---|
| 1 | 新版嵌套体（transportId = MAC） | 现状，凯迪拉克/DiPlay 都认 |
| 2 | 老版平铺体 `param0={1}` + DeviceIdentifier `00008110+MAC+0000`，原样与小写各发一份 | 参考实现 `useModernAvailabilityBody=false` |
| 3 | 不发 `0x4300`，只等车机自己发 `0x4301` | 参考实现「23 款」档 |

- 触发条件：发出 `0x4300` 之后整个等待窗口内 `Iap2LinkChannel.peerFrameCount` 一次都没涨
  （连纯 ACK 都没有）→ 记为该形态「静默」，下一轮自动换下一档，并打日志：
  `iap2 ⚠ 0x4300（…）发出后 8s 内车机零反馈……已记为静默，下一轮改用「…」`；
- 一旦某档拿到 `0x4301`（或继续推进）→ 立即定档，此后固定用它；
- 按车机身份持久化（`availability_body_memory`），重启不丢；
- **只在「新协议 + 声明会发 0x4301 + 没等到」这条路上启用**：老协议车机（Audi 等）
  不参与阶梯，避免回归；单测环境（无 Context）固定第一档，时序与改动前完全一致。

### 6.2 观察者代际 + 等待预算按「点击」计（`SessionController`）

- `pendingWatchGeneration`：新观察者一起来，旧的立刻退出；
- `pendingWaitBudgetStartedAt`：5 分钟从**用户点「启动连接」**算起，断链重连不重置；
- 预算耗尽 → 打一条结论日志（提示已试过各档报文体）、`phaseHint` 置为「本轮已停止重试」、
  拆掉保活链路，并置 `pendingWaitGaveUp` 让后续重连不再重复拆链/刷日志。

3. 更换档位后 `LINK rx` 是否恢复、`0x4301` 是否出现。

## 8. 第二轮补充解析（同一份日志，2026-10-26 21:10）

第一轮只回答了「车机为什么不推进」；第二轮把 1169 行逐类过了一遍，发现四处**我们自己的**
问题，其中一处直接让 5 分钟保活失效。

### 8.1 催问本身就是拆链元凶（最要紧）

把 `LINK tx` 与 `LINK rx` 数一下：**我方 215 帧、车机 48 帧**。多出来的全是重传：

```
20:30:02.672  seq=111 0x4e0a   ← 催问第 1 次补发的问候，走 send()（ACK 待确认）
20:30:06.678  seq=111 重传
20:30:10.677  seq=111 重传
20:30:14.678  seq=111 重传
20:30:25.689  LINK closed: packet 111 not acknowledged
```

车机自 `0x4300`（20:29:49.669）起就一帧都不回，于是**催问补发的四条问候**全部进重传队列，
4 次 × ~5.8s ≈ 23 秒后看门狗把链路拆掉——所以「42 秒一轮」不是车机断的，是我们自己断的。
催问的初衷是「多喂几次或许能唤醒它」，实测 6 轮 12 次 `0x4300` 全部零回应，反倒把
5 分钟保活切成 8 段空转，顺带让每轮都重跑一遍识别 + MFi。

改法（`nudgeIfDue`）：以 `0x4300` 发出时的 `peerFrameCount` 为基线，**车机零回帧时跳过催问**
（不消耗催问次数，每 4 次记一行），链路保持打开等晚到的 `0x4301`；一旦对端恢复回帧，
下一轮自动恢复催问。凯迪拉克那种「ACK 0x4300 但一直不发 0x4301」的车机不受影响——
它的帧数一直涨，催问照旧。

### 8.2 `0x4300` 其实每轮发了 3 次

`Phase 1` 1 次 + 两次催问各 1 次。所以这次复测不是「只发了一次 0x4300 就没反应」，
而是 **12 次都没反应**——「多发一次试试」这条假设已经被数据否掉了。

### 8.3 车机没死，是它的 iAP2 应用层没醒

`0x1D01` 之后车机一条 CSM 都没有（声明会发的 11 条里 0 条），但 RFCOMM 上每秒仍有
`ff 55 02 00 ee 10`。这 6 字节就是我们每一帧前面的**同一个封装头**（看 `RAW tx`：
`ff 55 02 00 ee 10` + iAP2 帧），所以它是「链路层还活着、应用层不出声」。
这也说明：靠「等链路超时」永远等不到结论，必须靠应用层消息判断。

### 8.4 车机自报三个传输组件（能力没有问题）

`0x1D01` 参数 `0x11 / 0x18 / 0x12`（别克 E2LB 与凯迪拉克 CT5 **逐字节相同**）：

| 参数 | 名称 | 组件号 |
|---|---|---|
| `0x11` | `CinemoBTComponent`（子参 3 带 `4C:92` 标识） | 2 |
| `0x18` | `CinemoWIFIComponent` | 3 |
| `0x12` | `CinemoHIDRemote` | 1 |

即：硬件与栈层面「蓝牙 / Wi-Fi / HID 遥控」三件都在，无线 CarPlay 的能力声明是完整的，
不推进只能是应用层没被唤醒。顺带留一个待验证问题：`0x4300` 内层那个 `1` 如果是**传输组件号**，
WiFi 应该是 `3`——现在按参考实现发 `1`，可作为下一轮实验项（日志已加一行
`iap2 0x1d01 传输组件：…`，方便对比不同车型）。

### 8.5 视频其实只有 20 fps，不是 60

`CARLIFE: 实测帧率 19.9fps（5s 内 100 帧，声明 60）`——**精确 20.0 封顶**，43 次采样无一例外
（前半段更低，15.4~15.8，是重连前的旧会话）。也就是说：

- 我们向车机声明 60fps，实际只喂 20fps；
- `98316` 改了两次 `fps=60` 也没突破；
- 之前 main 分支加的「省电模式 30fps」在这台手机上基本是空档（引擎本来就 20），
  **真正有效的省电杠杆是 I 帧间隔和暗幕压亮度**。

### 8.6 两个小问题

- `MEDIA: 通知监听器未被系统绑定` 连打 14 次：这台一加的通知使用权已授权但系统没绑定监听器，
  直接后果是**车机歌名会空**。需要到「设置 → 通知使用权」把本应用关掉再打开一次。
- `iap2 未收到 0x6800（该接收端不发 StartHID，继续）` 与上一行
  `可选消息声明：StartHID(0x6800)=会发` 自相矛盾——原文案写死了「不发」。
  已改成按声明区分：声明会发 → 「可能等 0x4300 之后才开 HID」；无清单 → 「按不发处理」。
