## 5. 与项目当前落地的对照（有结论价值）

1. **`Iap2IsDetectMarker` 自检异常有了解释线索**：JNI 确实导出了该函数，但 ABI 探针
   `nativeIap2IsDetectMarker`（Kotlin 传 String/ByteArray）拿到 `detectMarker=0`；
   需核对 native 端入参期望（可能期望特定 TLV 字节而非自定义字符串）。
2. **`SessionSendMediaLibrary` 已被导出但 Kotlin 未调用**——这正对应"车机媒体信息/封面缺失"
   问题：协议核已具备媒体库推送能力，只是 v2 的事件桥没接。比之前判断的"要 Rust 开放能力"
   更乐观——能力可能已经在 so 里，缺的是 Kotlin 调用。
3. **`AirplayScreenSealFrame` 存在且与 Kotlin 的修复调用吻合**：证明 1.2.80 v2 的 seal 修复
   方向正确（调的就是 native 导出的函数）。
4. **双 cipher（chacha / aesCtr）**：`AirplayScreenSealFrame` 返回的整帧头里带 cipher 标识，
   Kotlin 原样写出即可，不要二次加密（与已实施的修复一致）。

## 6. 局限

- 这是**静态解包**：符号/字符串/流程标签可靠；具体算法分支、参数语义需动态调试或反汇编 `.text`
  （`.text` 约 720 KB，clang LTO 优化后函数名大量内联，深入反汇编收益有限）。
- 未做任何逆向工程绕过授权；仅为理解本fork引入的二进制依赖的行为边界。
