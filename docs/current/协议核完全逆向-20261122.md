## 1. 二进制性质（逆向确认）

- Rust 1.99.1 + NDK r28c + clang 19，**半 strip**：`.symtab` 已删，但 `.dynsym` 保留全部导出。
- 两套 ABI：**118 个 JNI 函数**（给 Kotlin）+ **14 个 `cardeck_session_*` C 函数**（给 native，未 strip，见解包报告）。
- 无 `JNI_OnLoad`、无静态注册依赖——118 个符号名与 Kotlin `NativeBridge.external fun` 一一对应，**改包名必全废**（已验证过）。

## 2. 核心函数逆向契约（逐条）

### 2.1 `nativeIap2IsDetectMarker`（@0x9ac38，256B）——自检异常的根因

反汇编还原的判定逻辑：

```
输入: (JNIEnv*, thiz, jbyteArray data, jint len)
  len < 5 或 data==null → return false
  JNI GetArrayLength(data) < len → return false
  栈上开 4096B 缓冲（memset 0），GetByteArrayRegion(data, 0, len, buf)
  构造常量 x22 = 0x10ee_0002_55ff  (mov #0x55ff; movk #2<<16; movk #0x10ee<<32)
  即小端 6 字节魔数: FF 55 02 00 EE 10
  取 buf 前 6 字节 (ldrh [sp+4] | ldr [sp] 拼 48 位) 与魔数比较:
    len==5 且前5字节 == FF 55 02 00 EE  → true
    len==6 且前6字节 == FF 55 02 00 EE 10 → true (但需注意 0x9ad14 的边界复核)
  否则 false
```

**结论**：这个 JNI 只认 **`FF 55 02 00 EE 10` 这一串 iAP2 DETECT 报文魔数**，
不是任意字符串。之前 `ProtocolCoreProbe` 自检传的若不是这 6 字节，`detectMarker=0` 是**必然**的，
属探针入参错误，不是协议核行为异常。修法：探针改为喂这 6 字节（或干脆去掉该项自检）。

### 2.2 `nativeMfiChallengeSizeForCertificate`（@0x9addc，288B）——**从证书识别**挑战长度

Kotlin 签名（v2 `NativeBridge.kt:298`）：`(certDer: ByteArray, negotiatedMfi4: Boolean, authVerMajor: Int): Int`，
其中 `certDer` = 0xAA01 收到的对端证书 DER。反汇编还原：

```
输入: (JNIEnv*, thiz, jbyteArray certDer, w3=negotiatedMfi4, w4=authVerMajor)
  certDer==null 或 len<1 → return -1
  GetByteArrayRegion 取出证书 DER
  if (w3 != 0 && w4 != 0) → return 16        // MFi4 且版本条件 → 固定 16B
  if (w3 != 0)            → return 16        // negotiatedMfi4 → 固定 16B
  // w3==0: 解析证书
  v = parse_cert_field(certDer, len)         // 0xf8a58，深挖见下
  idx = (v & 0xff) - 2
  idx ∈ [0,3] → 查表 @0x22520 = [20, 32, -1, 16]   // v∈{2,3,4,5}→{20,32,-1,16}
  idx > 3     → return -1
```

解析函数 `0xf8a58` 完整逆向（四个出口，返回枚举 v=0~5）：

| v | 触发条件（证书 DER 扫描） | 查表结果 |
|---|---|---|
| 3 | 找到 9 字节 Apple OID `2a 86 48 86 f7 63 64 06 24`（1.2.840.113635.100.6.36） | **32B** |
| 4 | 找到 10 字节 Apple OID `…3b 01`（1.2.840.113635.100.6.59.1） | -1（无效） |
| 5 | 找到 10 字节 Apple OID `…47 01`（1.2.840.113635.100.6.71.1） | **16B** |
| 2 | 找到 15 字节 ASN.1 INTEGER，其 [2]/[6]/[8]/[11] 字节均为 `0xAA` | **20B** |
| 0/1 | 解析失败 | -1 |

检查顺序：32 → 无效 → 16 → 20。`0xf8a58` 逐层下钻 SEQUENCE (`0x30`) → 到 `0xA3`
**证书扩展区**后再找 OID (`0x06`)；前缀字节 `2a 86 48 86 f7 63 64 06` 是 Apple 私有 OID 弧
1.2.840.113635.100.6（`@0xf8c00` 构造常量 `0x0664_63f7_8648_862a`，长度 `cmp #9`/`cmp #0xa`）。
**此前报告写"公钥算法 OID（RSA vs EC）"并不准确，已更正为证书扩展区的 Apple 私有 OID。**

**结论（重要修正）**：MFi 三档 20/32/16 虽与 main 一致，但**选用机制根本不同**：
- 协议核：**读 0xAA01 证书 DER → 解析扩展 OID → 一次算出长度**（零试探）；
- main（原实现）：**发 challenge 试探 → 看应答/静默/0xAA04 → 换档重试 → `MfiLengthMemory` 按车机记忆**
  （`Iap2SenderSession.runMfiChallenge`）。这是"尝试"，不是"识别"——
  新车机 / 记忆丢失 / 固件变化时最坏要试 3 档（每档最长 6 秒）。

之前写"档位一致即等价"是错误结论，特此更正。该 JNI 在 v2 Kotlin 侧**无调用点**（仅签名定义），
是协议核内部 API 的暴露；但其揭示的"证书识别"规则已于 2026-11-22 回灌 main（见 §3.5）。

### 2.3 `nativeAirplayScreenSealFrame`（@0x915ac，600B）——帧密封

关键指令：

```
输入: (JNIEnv*, thiz, jlong handle, jbyteArray payload, jint ptsHi, ...)
  w5(第5参) → w20 保留; x4 → x21; x3 → x1; x2 → x22 (handle)
  GetByteArrayRegion 取 payload
  构造 16 字节 nonce (mov w4,#0x10)
  会话对象 +0x6d0 取 cipher 上下文，cmp ==2 → 疑似 cipher 类型判定
  会话对象 +0xed0 取密钥指针 (ldr x3,[x22,#0xed0])
  mov w2,#0x80 → 输出 128 字节头
  调用 seal 原语 (0xbd8e4) → 再 memcpy 128B 到输出 (0xbc918, w2=0x80) → 拼装整帧返回
```

**结论**：native **内部完成密封**（ChaCha/AES 选由会话 cipher 决定，头固定 128B），
Kotlin 拿到的是「128B 头 + 密文」整帧，直接写 socket 即可。这与昨天 seal 修复的实现完全吻合，
且证明**不能二次加密**（Kotlin 侧 CoreSealed 分支直接写整帧是对的）。

### 2.4 `nativeSessionSendMediaLibrary`（@0xd0cd4，844B）——媒体库推送（能力已具备）

```
输入: (JNIEnv*, thiz, jlong/x?, jint, jbyteArray mediaItems, ...)
  GetArrayLength(data) ≥ 1 (0x558)
  GetByteArrayRegion 取出 (0x5c0 / 0x600)
  解析 TLV: 每项 32 字节 (add x25,x9,#0x20)，ldrb 首字节 cmp #0xff 为结束标记
  构建媒体库消息并发送到会话
```

**结论**：协议核**原生支持媒体库推送**，入参是字节数组。**这推翻了之前"封面要 Rust 开放能力"的判断**——
native 侧能力已在，缺的是 Kotlin 侧构造这个 byte[] 并调用它。这是补歌名/封面最有希望的通道
（歌名也可能走 media library 而非 0x5001）。

## 3. 逆向对"主分支落地"的直接指导

用户要求：**以解包/逆向为主，主分支原有逻辑为辅**。据此，逆向给出的权威事实是：

1. **detect marker 魔数明确了** → main 的 `Iap2IsDetectMarker` 相关逻辑若判定 "FF55 marker"，
   应以 `FF 55 02 00 EE 10` 为准，不要用自造的报文头。
2. **MFi 三档 20/32/16 被逆向证实** → main 现有的 `MfiChallengeSizeForCertificate` 三档判定
   与协议核一致，保留。
3. **帧密封 = 128B 头 + native 密封** → main 若接协议核，遵守"native 密封、Kotlin 不二次加密"。
4. **MediaLibrary 原生可用** → main 要补歌名/封面，优先走 `nativeSessionSendMediaLibrary`，
   而不是自研 0x5001 双重封包（历史上踩过坑）。

## 3.5 main 分支落地结果（2026-11-22）

用户裁定「以逆向为主、main 原有逻辑为辅，只回灌逆向确认的事实」，逐项核对后：

| 逆向事实 | main 现状 | 处理 |
|---|---|---|
| DETECT 魔数 `FF 55 02 00 EE 10`（`nativeIap2IsDetectMarker` @0x9ac38）| `Iap2LinkEngine.MARKER` + `Iap2LinkPacket.splitFrames` 逐字节一致 | ✅ 真一致，补佐证注释 |
| MFi **从证书扩展 OID 识别**长度（`nativeMfiChallengeSizeForCertificate` @0x9addc → 解析 `0xf8a58` → 查表 `[20,32,-1,16]`）| 原先靠**试探 + `MfiLengthMemory` 按车机记忆**；虽有 `containsEcdsaPublicKeyOid` 调 32B 优先，但不是精确识别。2026-11-22 已回灌证书识别 | ✅ **识别优先 + 失败回退试探**（见下） |
| 帧密封 128B 头 + native 密封 | main 自研 ChaCha/AES（`StreamFrameCipher`）| 通道不同，能力对等，保持不动 |
| MediaLibrary 原生推送（byte[] TLV，`nativeSessionSendMediaLibrary` @0xd0cd4）| main 走 0x5001 NowPlayingUpdate + 封面 session 12，已覆盖歌名/封面 | 通道不同，能力对等，保持不动 |

**结论修正**（用户 18:29 质疑「一致的地方没有差异么？MFi 我们没识别只能尝试吧？」后深挖）：

- **DETECT 魔数是真一致**（逐字节同），这项之前的结论成立。
- **MFi 不是真一致**：档位数值相同，但协议核**从 0xAA01 证书扩展区 Apple OID 直接识别**长度，
  main 原先是**试探 + 车机记忆**。这是实打实的能力差异，「档位一致即等价」的说法错误，已在 §2.2 更正。
- **落地（用户 18:33 指令「做进 main，并在失败后恢复试探」）**：把 §2.2 的精确规则实现为纯函数
  `Iap2SenderSession` 同包的 `MfiCertificateLength.recognize(der): Int?`（扫描 Apple 私有 OID 与
  15B 扩展标记，返回 20/32/16 或 null），接入两条链路：
  - 蓝牙 `Iap2SenderSession.run()` 收到 0xAA01 后识别 → `runMfiChallenge` 插队首；
  - WiFi 隧道 `VirtualIap2Link` 收 MFI_CERTIFICATE 后识别 → `startNextMfiChallengeLocked` 插队首。
  **识别只做首选**：`MfiCertificateLength.prefer()` 把识别长度放到队首后，
  原「记忆重排 + 基线」顺序完整保留；该档 0xAA04 / 静默 / 断链时照原逻辑推进下一档。
  识别不出（null）时行为与改前完全一致。ECDSA 公钥 OID 与 `MfiLengthMemory` 均未改动。
- 验证：新增 8 例纯函数单测，全量 **976 例单测 0 失败**，编译通过。
  未做真机验证（识别是否命中取决于车机证书是否含 Apple 扩展 OID，日志会打识别结果）。
  按用户规则：只本地提交，不推送、不发版。

## 4. 局限与边界

- `.text` 经 clang LTO + PGO 优化，函数名内联严重、控制流扁平，逐指令还原全部语义不现实；
  逆向聚焦在**对外可判定的行为契约**（参数、魔数、常量、返回码、调用序列），这些结论可靠。
- 未做动态调试（需真机 + so 符号），秘钥派生/加密算法内部细节不解，也不打算解——
  这些是协议核的黑盒能力，主分支只需按契约调用，不需要重实现。
- 逆向目的仅为理解本 fork 引入的二进制依赖的行为边界，不涉及授权绕过。
