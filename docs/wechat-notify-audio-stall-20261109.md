# 微信提示音把音乐「卡一下」——根因与改法（2026-11-09）

日志：`CarPToCarL-log-20261109-093213.txt`（1.2.31 #oneperm，Audi_MMI_8349 / 荣耀 PTP-AN10）。

## 1. 现象与实证

用户在车上收微信消息，提示音一响，音乐明显卡顿一下。

日志里只有一次完整的中断，时间线（09:29:45）：

```
45.458  CARLIFE: 媒体 引擎音频停止（0x30003）——来电或音频路由被切走
45.458  CARLIFE: 引擎音频已停（来电 / 音频路由被切走）——车机侧这一段会静音
        …311ms、一个音频包都没有…
45.768  CARLIFE: 媒体 音频格式宣告 44100Hz 2ch 16bit
45.769  CARLIFE: 媒体 引擎音频开始（0x30002）
45.769  AUDIO: 引擎音频恢复 → 补发 3 个同步包重新对齐车机时钟
```

## 2. 根因

两条叠在一起：

1. **CarLife 引擎自己停媒体通道**。手机侧 CarLife+ 要为提示音切换音频路由，于是发
   `0x30003` 停掉媒体 PCM，311ms 后再 `0x30002` 恢复。这是引擎行为，我们改不了。
2. **我们在这 311ms 里一个包都不发**。`AudioSender` 的静音保活阈值是 300ms
   （`IDLE_FILL_AFTER_MILLIS`），而中断只有 311ms —— 几乎没补上帧。车机的 jitter buffer
   被排空，恢复瞬间要重新缓冲，听感就是「卡一下」，而不是「静音 0.3 秒」。

另外恢复时那句「补发 3 个同步包」其实也基本无效：同一场会话里
`同步包共发出 298 个，其中 293 次被车机 controlPort 的 ICMP 拒绝`——车机那个端口没在监听，
补发也到不了。

## 3. 改法（本轮）

| 改动 | 位置 |
| --- | --- |
| 引擎报 `0x30003` 时**立即**补静音（阈值 300ms → 0） | `AudioSender.beginIdleFill()` |
| 引擎报 `0x30002` 时恢复阈值 | `AudioSender.endIdleFill()` |
| 只有停 ≥ 2s 才补发同步包重对齐（短中断靠静音帧续时间戳，不重对齐） | `CarLifeHijack.onEngineAudioGate()` |
| 单拍补帧上限 12 → 16（100ms 一拍需要 13.6 帧，12 会让补帧永远慢一拍） | `MAX_KEEPALIVE_FRAMES_PER_TICK` |

效果：311ms 内的 RTP 时间戳保持连续，车机缓冲不排空 → 用户听到的是「静音 0.3 秒」，
但不再有恢复瞬间的那一下卡顿。**提示音本身在车机上仍然听不到**——它由手机播放，
不走 CarLife 的媒体/TTS 通道，我们无从捕获（要听得见，得靠 CarLife 自己的「消息播报」
走 TTS 通道，日志里本轮没有 TTS 包）。

## 4. 上车怎么验

提示音再响一次，看日志：

- `AUDIO: 引擎音频停止 → 立即补静音帧保持 RTP 连续` —— 新逻辑生效
- `CARLIFE: 引擎音频恢复（停 3xx ms，已由静音帧续上，不重对齐）` —— 短中断不再重对齐
- 听感：静音一下，音乐接上时**不再顿一下**

若反而出现「提示音后音乐有轻微重复」，把 `BEGIN_IDLE_FILL` 这条改回 300ms 阈值即可
（`AudioSender.beginIdleFill` 置 `idleFillAfterMillis` 的位置）。
