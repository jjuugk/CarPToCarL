## 一、车机控制读不到数据（1.2.18 + 618af5a）

### 现象

奥迪 MIB3（`Audi_MMI_8349` / `AUDI 4260`）上车后，MIB3 面板一直显示「等待 0xEA03 会话状态」，读不到任何车况数据。

### 证据（`CarPToCarL-log-20261104-083034.txt`，1.2.17）

三段会话**全部死在同一个序号 115**：

| 时间 | 事实 |
|---|---|
| 08:29:38.260 | `LINK rx ... ack=114` —— 车机最后一次确认 |
| 08:29:51.330 | 开始连发 8 条 `ea 04 {"id":1,"method":"GET","path":"/vehicleinformation"}` |
| 之后 | **再无任何 `LINK rx`**，连重传的 SYN 都不回 |
| 08:30:23.406 | `packet 115 not acknowledged` → 整条 iAP2 链路被拆 |

**`0xEA03` 在全文件出现 0 次。** 也就是说 EA 会话根本没建立，我们却往 0xEA04（EA 数据管道）里写数据；车机收到后不再回 ACK，我们的重传永远等不到回执，最后超时拆链——而这轮拆链会顺手杀死视频和音频。

第二个 bug：奥迪会**重复使用参数号 10** 声明三个 EA 协议（`com.audi.cpp.eadata1/2/3`），而旧代码用 `associateBy(参数号)`，把参数号当唯一键，三个协议只活下来一个 → `0xEA00` 只发了 `eadata1`。

### 改动

| 文件 | 位置 | 改了什么 |
|---|---|---|
| `mib3/Mib3ControlLink.kt` | `refreshReadOnly()` | 先查 `status().phase`；不是 `Phase.READY` 就**只记账不发 GET**，置 `pendingRefreshOnReady = true` 后返回 false |
| `mib3/Mib3ControlLink.kt` | `samplesFromStatus()` | 0xEA03 到达时用一次性线程 `mib3-refresh-on-ready` 补发被挡下的那轮 |
| `mib3/Mib3ControlLink.kt` | `attach()` | 复位块补 `pendingRefreshOnReady = false`；日志「EA 协议=无」→「待 0x1D01 解析（此刻身份还没到）」 |
| `iap2/Iap2Csm.kt` | 新增 `object Iap2Ea` | `parseProtocols(body)` 按出现顺序收集**所有**参数号 10/11/12，返回 `(参数号, 协议号, 协议名)` |
| `iap2/Iap2SenderSession.kt` | `parseEaProtocols()` | 改为委托 `Iap2Ea.parseProtocols`，每个协议各打一行 `iap2 0x1d01 EA 组件[10] protocol=3 name=…` |
| `iap2/Iap2SenderSession.kt` | 新增 `scheduleEaSessionRetry()` | `0xEA00` 发出 8 秒仍未收到 `0xEA03` 就补催一轮；常量 `EA_RETRY_DELAY_MILLIS = 8_000L`，标志 `eaRetryScheduled` 防重入 |
| `bt/Iap2BluetoothClient.kt` | `object BtSessionGate` + `connectLoop` + `runSession` | 控制链路中途掉线不再直接放弃：登记 `linkLostPeerAddress/linkLostAt`，**只对掉线那台**在 `LINK_RECOVERY_WINDOW_MILLIS = 180_000L` 内单独补连；期间不计 `targetFailRounds`、不切 `awaitCarInitiated`；`manualTeardown` 时（用户主动断）不触发 |
| `iap2/Iap2SenderSession.kt`（618af5a） | `recvNewFrame` 收帧处 | 0xEA03 **进 expect/暂存区之前**就记 `eaStatusRaw` —— 否则它以「非目标帧」身份躺在 `receivedFrames` 里，催问线程会冤枉地补发一轮 0xEA00 |

### 验证（上车看这三行）

```
MIB3: 0xEA03 已到——补发被挡下的那轮只读 GET
iap2 0x1d01 EA 组件[10] protocol=3 name=com.audi.cpp.eadata1
iap2 0x1d01 EA 组件[10] protocol=? name=com.audi.cpp.eadata2   ← 三个协议都该出现
```

若仍是 `本轮不发只读 GET（EA 会话未建立…）`，说明车机压根没给 EA 会话——那是车机侧策略问题（C8-4580 固件报告 §5.7 证实 EA 就是车控数据的承载管道），不在我们这层。

## 二、首连「导航有声、音乐无声」（1.2.18）

### 现象

首次连接后：TTS 导航播报有声音，音乐没有；**断开重连一次就正常**。

### 证据（同一份日志）

| 时间 | 事实 |
|---|---|
| 08:26:19.751 | 音频流协商成功 → **65 秒一个包都没有** |
| 08:27:24.976 | TTS 16k 单声道出声（正常） |
| 08:27:39.216 | 媒体 44.1k 立体声、电平 99%，**仍然没声音** |
| 08:28:41 | 重连后流一建立 **0.4 秒**就有包 → 立刻正常 |

差别只有一个：「流建立后先静默了多久」。真 iPhone 的音频流是**连续**的，没声音也一直送静音帧，接收端据此维持解码/播放管线与 RTP↔NTP 时钟；停一分钟再突然来音频，管线已被判空闲，包照收不放。

### 改动（`audio/AudioSender.kt`）

| 项 | 值 / 行为 |
|---|---|
| 新增常量 | `KEEPALIVE_TICK_MILLIS = 100L`、`IDLE_FILL_AFTER_MILLIS = 300L`、`MAX_KEEPALIVE_FRAMES_PER_TICK = 12` |
| 新增字段 | `lastRealFeedAt`（最近一次**真实** PCM 时刻）、`keepAliveThread` |
| `startPassthrough()` | 末尾调 `startSilenceKeepAlive()` |
| 新增 `startSilenceKeepAlive()` | 线程 `audio-silence-keepalive`：超过 300ms 无真实 PCM，按实时速率 `dispatchPcm(静音帧)` 补，真实 PCM 回来立刻停；每拍最多补 12 帧防止卡顿后猛灌；首补打一行日志 |
| `feedPcm()` | 在 `alignPcm` **之前**更新 `lastRealFeedAt`（对齐会缓冲，不能拿它当「有数据」） |
| `sendPayload()` | 加 `@Synchronized` —— 补静音线程与注入线程会并发改 `sequence/timestamp/nonceCounter/markerPending` |
| `stop()` | `keepAliveThread?.interrupt(); keepAliveThread = null` |

### 状态

**这条仍是假设，待上车验证。** 已排除：`controlPort 6011` 全程 ICMP 不可达这件事在有声的第 2/3 轮同样存在，与有没有声音无关；`MediaSessionsState` 暂停联动未触发；音频负载本身正常（首帧 557B、`21 21 45 00` 头、电平 99%）。

验证看：`AUDIO: 无 PCM 超过 300ms——开始补静音帧保活`，以及音乐第一段是否出声。

## 三、画面不出来（1.2.19 的前 11 个提交）

这部分是 10:01 ~ 15:09 连续 11 个提交，全部围绕**「车机不切屏 / 黑屏」**，最终收敛成三条独立机制。按时间顺序看容易乱，这里按**问题**归类。

### 3.1 根问题：CarLife 引擎的编码尺寸定档，只有一次机会

`98311`（`HU_VIDEO_ENC_INIT`，视频编码初始化）是车机告诉 CarLife 引擎「我的屏幕多大」的**唯一**通道，而引擎**只在创建编码器之前**认这个值：一旦编码器起来，再改它只回一个「确认参数」，实际编码尺寸不动。

而时序天生错位：CarLife+ 端口一开我们就得握手（`CarLifeHijack.prewarm`），那时**还没连车机**，AirPlay `/info` 里的车机画布往往晚 10~20 秒才到。结果首轮 98311 永远报默认 1280×720，等知道了画布已经晚了。

围绕这一条，今天打了五个补丁：

| # | 提交 | 机制 | 默认 |
|---|---|---|---|
| a | `914b670` | **记住上次车机画布**：同一台车下次开机先按上次画布申请，引擎建编码器即对齐。新增 `carlife/CarCanvasMemory.kt`（只记车机真正通告过的画布，手机横屏兜底值不落盘；`sanitize()` 丢弃 0/离谱值） | 开 |
| b | `960ed1f` | **有序初始化**：先 98386（`DISABLE_RESOLUTION_OPTION=1` 分辨率直通）→ 等引擎确认（`MD_FEATURE_CONFIG_DONE`）→ 才发第一条 98311。实证：唯一拿到 1412×654 的那次（13:18:53）就是 98386 先被接受、0.45s 后才发 98311；另外三次都是 98311 抢跑 → 引擎当场按白名单定档 720p | 开（`carlife_ordered_init`） |
| c | `61cff27` | **98311 去重**：同一组 `宽x高@帧率` 在 `ENCODER_INIT_DEDUPE_MS = 5_000L` 内只发一次。引擎收到尺寸未变的重复 98311 会把 65544 确认值降成 1280×720@20（实测 4/4） | 开 |
| d | `c5c4fbd` | **首帧后二次初始化**：65544 会原样回申请值（看着像成功），SPS 才是真相。首帧后 `SETTLE_REINIT_DELAY_MS = 2_500L` 再走一次 98386→98311，让引擎在**已有编码器**上重建 | **关**（`carlife_settle_reinit`，实验项） |
| e | `c3ec073` | **CONNECT_TYPE 自动探测**：确认值 ≠ 申请值时，一轮会话内轮换 1~8 撞档位表，命中即停。正常车机第一轮就满足「确认=申请」，当场结束 | **关**（`carlife_connect_type_probe`，实验项） |

### 3.2 VideoConfig 画布声明：从「必须=码流」改成两种模式

| 提交 | 内容 |
|---|---|
| `90bee9f` | `VideoSender` 新增 `canvasSize` 回调，VideoConfig 头声明改回车机画布（奥迪 1412×654 整屏黑的反向尝试）；新增 `resolveConfigSize()` 可单测；「画布 ≠ 码流」提示每轮只打一次 `canvasMismatchLogged` |

| `e4b8afc` | **分离「解码尺寸」与「显示视口」**：`buildVideoConfigHeader(..., viewArea)` 把视口写到 `VIEW_AREA_ORIGIN_OFFSET = 32`（x/y）与 `VIEW_AREA_SIZE_OFFSET = 40`（宽/高），两个 f32 LE。4580 的解析器是 `32/36` 读 x/y、`40/44` 读宽高 —— 于是「按码流解码 + 按画布显示」可以同时成立，不再二选一 |

### 3.3 画面链路的完整判据（文档 `docs/mib3-carplay-display-contract.md`）

固件原文只有 4 条日志模板（`CL3D_MIB3H` × `CDSICarplayImpl`）：

```
[CDSICarplayImpl] <DSI> resourcesRequest="%s", applicationsRequest="%s", reason="%s"
[CDSICarplayImpl] <DSI><SCREEN> Video state='%s'        // active / inactive
[CDSICarplayImpl] <SCREEN> State changed: %s --> %s
[CDSICarplayImpl] <ERROR> Failed to overtake the screen: "%s"
```

顺序是：**modesChanged（声明持有主屏）→ 主屏流 SETUP 且 uuid = `/info displays[].uuid` → 帧真的到且解码成功（Video state=active）→ 仲裁批出 `CarplayScreenRequest` → HMI 让屏**。

**「连接成功」本身不是唤起画面的条件。** 判断只看三行有没有同时出现：

```
AIRPLAY: modesChanged（声明持有主屏/主音频资源）[200]
AIRPLAY: ✓ 主屏流协商成功 dataPort=…
VIDEO:  帧 #N … 已发送            ← 这条停了就是没有画面
```

## 四、4580 断开后连不上（1.2.19 三改 → 1.2.20 补两条）

### 现象

4580 只有第一次能连上；断开后一直卡在「加入 WiFi」或「AirPlay 配对」。

### 固件依据（`docs/mib3-firmware-c8-4580.md`）

| 配置项 | 值 | 含义 |
|---|---|---|
| `mediaDisconnectTimeout` | **15000 ms** | 蓝牙断开要满 15 秒，车机才把设备判成「已移除」 |
| `iap2CarplayAvailabilityWaitTimeout` | 60000 ms | 等不到 CarPlay 可用性就踢出 pending 列表 |
| `teardownTimeout` / `cleanupTimeout` | 2000 / 2500 ms | 会话收尾 / 清理 `/var/appdata/carplay` |
| `carplayHTTPConnectionTimeoutMs` / `httpRetries` | 800 ms / 2 | 连我们 AirPlay 的 HTTP 口 |

关键日志模板（`CDeviceDetection`）：

```
[CDeviceDetection] isDeviceActiveApp=%u, deviceID=%u, connectionType=%s, keepIAP2Session=%d
[CDeviceDetection] IAP2 session already running. Waiting for required IAP2 information.
```

即：**15 秒内设备再次出现，车机认为它还是 `activeApp`（`keepIAP2Session=1`），只「等 required IAP2 information」，既不新建会话也不启动 projection** —— 表现为接受 RFCOMM、走完身份交换、给热点凭据，但 7000 端口不开、mDNS 不广播、0x4301 不回。

EA 侧还有泄漏保护：`EAP session … already exist`、`another session is already running` —— 会话没收干净会直接挡住下一次。

### 1.2.19 三改（`fdbbd98`）

| # | 文件 | 改动 |
|---|---|---|
| 1 | `iap2/Iap2SenderSession.kt` | 新增 `closeEaSessions()`：断开前发 `0xEA01 StopEASession`。三个「不发」判据：没声明过 EA 协议 / 链路已关 / **对端超过 `EA_CLOSE_PEER_IDLE_MILLIS = 5_000L` 没回过任何帧**（停摆了，写了也没人处理） |
| 2 | `transport/Iap2LinkChannel.kt` | 新增 `millisSinceLastPeerFrame()`（对端最后一帧距今毫秒，没收到过返回 -1）、`peerFrameCount`，供上面判据用 |
| 3 | `bt/Iap2BluetoothClient.kt` | `RETRY_DELAY_MILLIS` **3_000 → 16_000**；`RETRY_BACKOFF_MILLIS` **3/10/20s → 16/20/30s**；`PASSIVE_FALLBACK_ROUNDS` **3 → 2**（单轮已 16 秒，轮数必须降，否则切一次被动要等 48 秒） |
| 4 | `bt/Iap2BluetoothServer.kt` / `Iap2BluetoothClient.kt` | `detachCurrentSession()` / `stop()` 都先收 EA 会话再关 socket |
| 5 | `net/WifiCarPlayConnector.kt` | 新增 `isAssociatedTo(ssid)` / `adoptIfAlreadyConnected()`：系统本来就还连在车机热点上时直接 `bindProcessToNetwork`，不再发 specifier 弹确认框；读不到 SSID（`<unknown ssid>`）时不猜，走原路径 |

> **别把 16 秒调回去。** 低于 15 秒就会把车机的「设备移除」计时器一次次续上，它永远停在 `keepIAP2Session=1`。

### 1.2.20 补两条死路（`2624032`）——1.2.19 上车仍复现后重新定位

1.2.19 实车日志（OPPO PLG110 / Android 17，1.2.19）暴露两条**新的**死路：

**（一）网关兜底把唯一通的 IPv4 路由丢了**

兜底只取「第一条默认路由」的网关，这台车机排第一的是 **IPv6 链路本地** `fe80::1086:3aff:fe8d:9239`，于是 8 次重连全打在这个从没通过的地址上；而同一次会话的 mDNS 明明给过 `10.174.189.1:7000`。

| 改动 | 内容 |
|---|---|
| `net/WifiCarPlayConnector.kt` | `gatewayAddress()` → **`gatewayAddresses(): List<String>`**，收集**全部**默认网关、去 `%zone`、**IPv4 排最前**；`gatewayAddress()` 保留为首选。`isAssociatedTo()` 补 ConnectivityManager 路径（应用专属网络下 `WifiManager.connectionInfo` 报 `<unknown ssid>`） |
| `SessionController.kt` | 兜底改为 `EndpointHosts.candidates(gatewayAddresses())`，日志改成 `兜底使用网关地址 A / B:7000（…N 个候选按 IPv4 优先）` |

**（二）手动断开后没给车机冷却**

那轮是 `16:22:32.519` 断开、`16:22:33.696` 重连 —— **1.2 秒**，精确落在 `keepIAP2Session=1` 分支里。

| 改动 | 内容 |
|---|---|
| `bt/Iap2BluetoothClient.kt` | `BtSessionGate` 新增 `REACTIVATE_COOLDOWN_MILLIS = 18_000L`、`noteManualStop()`、`sinceManualStop()`；`connectLoop` 开头算出 `cooldownLeft`，>0 就 `sleepQuietly(cooldownLeft + 200)` 再拨 |
| `SessionController.kt` | 手动断开时 `BtSessionGate.noteManualStop()` |

### 验证（上车看这几行）

```
BT-C: 距上次手动断开只有 N 秒——车机要 18 秒才认为设备已移除（固件 mediaDisconnectTimeout=15s），先等 N 秒再发起
>>> mDNS 未发现，兜底使用网关地址 10.174.189.1 / fe80::1086:…:7000（2 个候选按 IPv4 优先）
EA: 已发 N 条 0xEA01 结束 EA 会话
WiFi: 系统已连在 "…" 上——直接复用
```

**IPv4 必须在最前面。** 如果连 `10.174.189.1:7000` 也超时，说明车机 7000 真的没开 —— 问题回到「它为什么不启动 projection」，解法要换成「断链后不主动拨、纯监听等它连进来」（**未做**，等这轮结果）。
