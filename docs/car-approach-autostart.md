# 靠近车机自动启动 / 自动连接（car approach autostart）

> 版本区间：1.2.0 → 1.2.6　　最后更新：2026-10-30
> 相关提交：1.2.2 `96a8713`（改为前台发起）、1.2.3 `e29d4e9`/`e6cc25e`（通知可看可断、
> 静默触发、后台启动被拦兜底）、1.2.4 `b98eefa`（远离 30 秒收摊）、1.2.6 `c5fa231`
> （划掉任务收摊、抑制加时限）

## 1. 这个功能解决什么

车机（尤其自带热点/无线 CarPlay 的车机）在手机进入范围后会**自己回连手机的蓝牙**。
本功能把这条"车机主动来找手机"的信号，变成"手机自动把 App 拉起来并连上车机"：

- 不用掏手机、不用点图标，上车即连；
- 检测是**静默**的：不扫描、不轮询、无常驻服务、无常驻通知；
- 手机端要**抢在系统自带车联之前**把链路占住（自带车联连不上这台车机，但会先抢一次蓝牙）。

## 2. 三个开关（首页「连接准备」）

| 开关 | 偏好键 | 默认 | 作用 |
|---|---|---|---|
| 靠近车机自动启动 | `car_approach_autostart` | 开 | 命中目标车机时把 App 拉到前台并自动连接 |
| 触发后不弹出界面 | `car_approach_silent_ui` | 关 | 界面完整建起后 1.2 秒退到后台，状态与「断开」都在通知栏 |
| 启动后自动连接 | `AutoConnectPrefs` | 开 | 冷启动即自动发起连接（自动拉起这条路也依赖它） |

另有「目标车机」（`TargetDevicePrefs`）：**未指定目标车机时本功能完全不动作**，
避免连到耳机、手表、别人的手机。

## 4. 为什么必须"拉到前台"，不能后台直连（1.2.2 的实车结论）

1.2.0 最初的实现是：接收器收到广播后**不等界面**，直接在后台起一轮
`SessionController.startConnection()`。链路确实建起来了（RFCOMM 建连、iAP2 握手能过），
但**车机端收不到任何数据**。

根因：整条管线不止 iAP2 拨号，还有

- CarLife 劫持（7240 端口监听/接管）；
- 虚拟屏与编码器（MediaProjection 授权、虚拟显示器创建）；
- 启动自检 `detectResidualDisplays()`（清残留虚拟屏）；
- 权限门禁（通知、蓝牙、悬浮窗、录屏授权）。

这些都挂在 **Activity 这一路**上。绕开界面直接连，握手能过，"出流"那一段起不来。

所以现在接收器**只做一件事：把 App 带到前台**，连接交给前台的完整流程。

## 5. 文件职责

| 文件 | 职责 |
|---|---|
| `bt/CarApproachReceiver.kt` | 静态注册收 ACL_CONNECTED / ACL_DISCONNECTED；判定命中后拉起界面；拉起失败兜底通知 |
| `bt/CarApproachPolicy.kt` | 纯函数判定（TRIGGER / NOT_TARGET / THROTTLED / SUPPRESSED…）；抑制窗口计算 |
| `bt/CarApproachPrefs.kt` | 偏好：开关、静默 UI、上次触发时刻、抑制位、ACL 连接状态、授权引导节流 |
| `bt/CarIdlePolicy.kt` | 纯函数：远离 30 秒到点该不该收摊（STILL_CONNECTED / STREAMING / UI_VISIBLE / CLOSE） |
| `bt/CarIdleGuard.kt` | 起/撤 30 秒闹钟；执行收摊（结束会话 → 停服务 → 清通知 → 可选退进程） |
| `bt/AppUiPresence.kt` | 界面存在性：`lastBringUpAt`（拉起是否真的生效）+ `isVisible`（前台可见计数） |
| `service/CarIdleReceiver.kt` | `exported="false"` 的闹钟接收器，只收应用内 action |
| `service/CarPlayService.kt` | 保活前台服务；通知（状态 + 断开动作）；`onTaskRemoved` 划卡片收摊 |
| `service/NotificationActionReceiver.kt` | 通知栏「断开」→ 走统一收摊路径 |

## 6. 判定规则（CarApproachPolicy）

命中 `TRIGGER` 需要**全部**成立：

1. 开关打开；
2. 已指定目标车机，且事件地址与之相等（大小写不敏感）；
3. 当前没有会话在跑、也没有正在连接；
4. 不处于「刚手动断开过」的抑制窗口（10 分钟）；
5. 距上次触发 ≥ 90 秒（`RETRIGGER_INTERVAL_MILLIS`，防断连重连时反复拉起）。

**抑制窗口为什么要有时限**：抑制原本只在 `ACL_DISCONNECTED` 时清除。但"人在车上把 App
关掉"之后蓝牙一直连着、永远等不到 ACL_DISCONNECTED，标记就永久挂着——用户还在车里却
再也唤不醒。现在 10 分钟自然失效；用户主动点开 App 立刻清除（自动拉起那一轮不清，
免得自己解除自己的防抖）。

## 7. 收摊（三个入口，同一条路径）

| 触发 | 条件 | 是否抑制自动启动 |
|---|---|---|
| 目标车机 ACL 断开满 30 秒 | 没链路 + 没推流 + 界面不在前台 | 否（车机已走，下次靠近应直接触发） |
| 通知栏点「断开」 | 立即 | 是（车机可能还连着，防断开/重连死循环） |
| 从最近任务划掉 App | 立即（`onTaskRemoved`） | 是（同上） |

30 秒窗口是给"车机重启/信号抖动后自己回连"留的：期间回连即撤销计时。
判定用 `isStreaming()`（画面真的在送）而**不是** `isSessionRunning()`——后者在
"点过启动连接、蓝牙服务正监听等回连"时长期为 true，拿它当阻断条件会让收摊永不触发。

退进程不影响静默检测：`ACL_*` 属隐式广播豁免，进程被杀后系统投递时会重新拉起静态接收器。

## 8. 权限要求

| 权限 | 作用 | 缺失后果 |
|---|---|---|
| `BLUETOOTH_CONNECT`（12+） | 读广播里的设备地址 | 无法识别是不是目标车机（日志留一行线索） |
| 通知权限（13+） | 保活通知、被拦提示 | 后台连接无可见入口 |
| **显示在其他应用上层** | Android 10+ 后台启动界面的豁免条件 | **静默拒绝**：`startActivity` 不报错，界面就是不出现 |
| 忽略电池优化 | 保证进程不被过早回收 | 广播投递延迟/被掐 |
| 自启动/关联启动（ROM 级） | MagicOS/HarmonyOS 等 | 广播根本投不到本应用 |

最后两项无法用代码申请，首页「连接准备」里有引导入口（各 7 天最多提示一次）。

## 9. 日志关键字（排查用）

| 关键字 | 含义 |
|---|---|
| `APPROACH: 检测到目标车机…已拉起 App` | 命中并已把启动请求交给系统 |
| `APPROACH: 未授予「显示在其他应用上层」` | 拉起前就缺权限，很可能被静默拦掉 |
| `APPROACH: 系统没有让 App 到前台（后台启动被拦）` | 3.5 秒核章失败，已发兜底通知 |
| `APPROACH: 车机已靠近，但已有会话 / 刚手动断开过` | 判定为 SESSION_RUNNING / SUPPRESSED |
| `APPROACH: 车机蓝牙链路断开——30 秒内未回连将…` | 收摊计时开始 |
| `IDLE: 车机已远离（蓝牙断开 30 秒未回连）` | 收摊执行 |
| `IDLE: 车机蓝牙已断开 30 秒，但画面仍在推送` | 因投屏中而不收摊 |
| `APPROACH: 静默触发——界面不停留` | 静默模式生效 |
