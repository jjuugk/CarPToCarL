# 别克「大连屏」连接档：它和现有连接池是什么关系

> 2026-10-31 立项，随 `bieke` 分支发布。实现：`buick/ConnectionProfile.kt`（档位 +
> `DisplayTuning`）、`SessionController`（建链时按档位定帧率）、`MainActivity`（下拉项与提示）。
> 参考对象：`CarDeck 0.1.28 别克适配版`（`Downloads/CarDeck-0.1.28-别克适配版-源码/cardeck-buick`）。

## 1. 这次加了什么

「连接配置」下拉框里新增一项：

| 档位 id | 显示名 | 建链 | 帧率 | 方向 |
|---|---|---|---|---|
| `buick_bigscreen` | **别克 大连屏（车机发起）** | 强制 B233 | **跟车机 `maxFPS`** | 等车机接入 |

它面向的是**另一台别克**——30 吋级一体式宽屏车机（GL8 / 世纪 / 君越那一类）。写这个档位时
手上**没有这台车的任何日志**，所以三条设计都是「先给一个最可能成立的起点，再留好退路」：

1. **建链先按 B233**。同属 SAIC-GM 8155 / Cinemo 栈家族的概率最大，75 字节双 group 的
   `0x4300`、32 字节 MFi、不发 `0x5702`、不拆 HFP/A2DP——这套已经在别克 E5 上跑通过。
2. **判定只认「用户显式选了这个档」**，不做任何品牌/型号猜测（原因见 §3）。
3. **方向默认等车机发起**。真不连就改选「别克 E5（手机拨号）」，两档共享同一套拨号闸门
   （首次 1.5 秒入站优先窗口、两次拨号至少间隔 15 秒）。

与别克 E5 档的差别只有三处，其中帧率那条是**全局规则**（所有档位都生效），不是大屏档专属：

**车机报 `maxFPS` 就跟随。** 接收端 `/info displays[0].maxFPS` 是它解码能力的自述，发得比它快
只会丢帧、堆解码队列。所以：

```
targetFps = min(本地偏好 60, 车机 maxFPS)      // 车机报了
targetFps = 本地偏好 60                         // 车机没报（通用/别克各档）
targetFps = 30                                  // 车机没报，且档位声明了兜底（大屏档）
```

车机报得比本地偏好高（如 120）时不抬高——上限始终是本地偏好。报出荒谬值（如 10）时按 24 兜底，
避免卡成 PPT。**没报时只有大屏档退回 30**：大屏车机普遍 30，宁可保守，也不要在拿不到信息时
按 60 硬发；其余档位保持旧行为，保证「没有车机信息时与 1.2.7 一致」。

另外选档时会提示一次缩放建议（90%，参考项目同尺寸屏的取值），但**不自动改用户设置**：
显示参数是用户自己在「显示」面板调过的，悄悄覆盖会让人以为设置丢了。

## 2. 两套「连接池」的区别

这是本次最值得写下来的一段——**参考项目和本项目的连接池，设计哲学是反的**。

### 参考项目：车机画像（`iap2/ReceiverProfile.kt`）

一份**只读的纯函数画像**，把三处信号收口成判定：`0x1D01` 身份帧（品牌/型号/收发消息清单）、
mDNS 与 `/info`（features 位图、srcvers、HID 描述符）、实车行为（MFi 挑战长度、拆链特征，
走 Memory 学习）。产出三个维度：

- `Era`：`PRE_HOMEKIT` / `OPTIONAL_PAIRING` / `MODERN`（按 features bit38 = HK_PAIRING_AND_ENCRYPT）
- `WifiGen`：`LEGACY` / `NEW`（按收发清单里有没有 `0x5703`/`0x5702`）
- `LinkGeneration`：`CLASSIC_MIB3` / `EVENT_LINK`（制造 + 型号 + 清单稀疏度三条同时命中）

它有两条写进注释的「铁律」：

> 1. **按能力分支，不按版本号/品牌硬编码**；2. **判定必须可解释**——`describe` 把依据写进日志。

### 本项目：显式档位（`buick/ConnectionProfile.kt`）

一份**用户手选**的枚举，五档：自动识别 / 通用 / 别克 E5（车机发起）/ 别克 E5（手机拨号）/
别克 大连屏（车机发起）。配套三个东西：

- `B233Identity`：**硬编码品牌判定**——蓝牙名 `BUICK_[0-9]{4}` 只做线索，身份认 `0x1D01` 文本里
  「buick + saic general motors + (b233|e2lb)」三个标记齐全；
- `B233Selection`：档位 × 目标地址 × 蓝牙名 × 历史观测，决定这一轮是否走 B233；
- `B233DialPolicy`：拨号闸门，被动档永不主动拨。

### 对照

| 维度 | 本项目（bieke） | 参考项目（CarDeck 别克适配版） |
|---|---|---|
| 载体 | `ConnectionProfile` 枚举，用户显式选择，SharedPreferences 持久化 | `ReceiverProfile` 纯函数画像，自动判定，无用户选项 |
| 分派依据 | 品牌/型号文本 + 用户档位 | features 位图、srcvers、收发清单、HID 描述符等**能力信号** |
| 品牌硬编码 | **有**（`B233Identity` 三个标记） | **刻意避免**（注释明确「按能力分支，不按版本号/品牌」） |
| 学习机制 | `AvailabilityBodyMemory`（`0x4300` 体形态：单 group / 双 group / 版本号） | 三套 Memory：MFi 挑战长度、音频档位、可用性体 |
| 建链方向 | 显式两档（车机发起 / 手机拨号） | 无开关，按车机行为推进 |
| 帧率 | 车机报了 `maxFPS` 就跟随（没报则本地 60） | 默认 30（针对 1972×520@30 的大屏，无「跟随」概念） |
| 失败兜底 | 用户改档位一键退回「通用」 | 无（画像判定错了只能改代码） |
| 可解释性 | 日志一行 `CONN: 档位「…」→ …` | `describe()` 输出每条结论对应的信号原文 |

### 为什么不直接把参考项目那套搬过来

三句话：

1. **参考项目的画像需要信号，而大连屏这台车连身份都还没采到**。没有 `0x1D01` 文本、没有
   `/info`、没有清单，`ReceiverProfile.classify()` 全部会落到 `UNKNOWN`——搬过来也判不出东西。
2. **本项目已经付过「硬编码」的代价，也吃到了「显式档位」的甜头**。别克 E5 那次踩的是反面：
   只认 `b233` 一个型号标记，而真车回的是 `model=E2LB`，整条专用分支永远不命中，
   发出通用单 group 的 `0x4300` 被车机静默丢弃。补 `e2lb` 之后才通。这条教训说明
   **品牌型号判定可以做，但必须有「用户强制」这条兜底通道**——这正是档位存在的意义。
3. **没有日志时的自动识别 = 猜**，猜错的代价是「本来能连的车连不上」。所以这次的做法是：
   把最可能成立的规则包成一个**用户可选的档位**，实车跑一轮、拿到日志，再决定要不要把它
   并进 `AUTO`。

结论：**短期用档位，长期学画像**。等这台车的 `0x1D01` 与 `/info` 采到，应该做的不是再写一个
if，而是把「帧率跟车机上限」「HID 逻辑上限换算」这类**能力规则**提取成画像维度，
让 `AUTO` 自己认出来——那时这个手选档可以降级成「诊断用」。

## 3. 新档与现有别克档的逐条对比

| | 别克 E5（车机发起） | 别克 E5（手机拨号） | **别克 大连屏（车机发起）** |
|---|---|---|---|
| 强制 B233 | 是 | 是 | 是 |
| 没选目标设备时是否命中 | 否（要名字像别克或有过历史） | 否（同左） | **是**（选了就认） |
| 建链方向 | 等车机接入 | 手机主动拨号（间隔 ≥15s） | 等车机接入 |
| 帧率 | 车机报了 `maxFPS` 就跟随，没报则 60 | 车机报了跟随；没报则兜底 30 | 车机报了跟随；没报兜底 30 |
| 缩放建议 | 无 | 无 | **90%（仅提示，不落盘）** |
| 实车状态 | E2LB 已验证 | 车机不主动连时用 | **未验证** |

「没选目标设备也命中」是这次特意加的（`forceWhenNoTarget`）：大屏车机的蓝牙名几乎肯定不叫
`BUICK_xxxx`，如果还要求「名字像别克」才生效，用户选了档位等于白选。**一旦指定了目标地址，
仍然只认那一个地址**，防止连到旁边的耳机或另一台车——这条由单测守着。

## 4. 参考项目里值得借、但这次**没做**的三件事

按价值排序，都是「实车连上之后再动」的：

1. **HID 逻辑上限换算**（`input/TouchReports.kt`、`TouchRouter.setCoordinateScale`）
   别克触摸 HID 描述符声明的逻辑上限是 **3082×814**，而 AirPlay 显示是 **1972×520**，
   直接把原始 u16 当显示坐标会让触点整体偏大约 1.56 倍。参考项目从 `/info` 的
   `hidDevices[].hidDescriptor` 解析 Generic Desktop 的 `Logical Maximum` 来换算。
   本项目已有 `TouchRouter.setCoordinateScale`，但换算基准是「车机通告视图尺寸 → 流尺寸」，
   **没有 HID 逻辑上限这一层**。若大连屏出现「点哪都偏右下」或「点 A 中 B」，就是这里。
2. **隧道 MFi 直接发 32B**（`airplay/VirtualIap2Link.kt`）
   参考项目实测：WiFi 隧道的虚拟链路按 20B→32B→16B 逐档重试共耗 12 秒，超过车机约 10 秒的
   隧道超时，车机直接 reset 事件通道。别克隧道改为直接发 32B、超时不降级。
3. **MediaProjection 被误清空**（`service/CarPlayService.kt`）
   自动连接会建第二个投影，旧投影被系统回收时同样回调 `onStop`，参考项目原先无条件把
   `mediaProjection = null`，把刚建好的新投影一起废掉，后续音频报「缺少投屏权限」。
   这是通用缺陷，与车型无关，值得单独评估本项目是否有同样问题。

参考项目还做了「默认 90% + 30fps 的一次性迁移」；本项目不做自动迁移（理由同 §1 末——
不擅改用户设置），改为选档时提示。

## 5. 实车验证清单

**准备**：手机装 `1.2.7-bieke` 及以上；「连接配置」选 **别克 大连屏（车机发起）**；
「蓝牙配对」里把目标车机指定为这台车（这样别的设备不会被误连）。

按顺序看日志（关键字）：

| 日志 | 期望 | 不符合时怎么办 |
|---|---|---|
| `CONN: 连接配置改为「别克 大连屏（车机发起）」` | 选中即出现 | — |
| `CONN: 档位「别克 大连屏（车机发起）」→ 目标帧率 30fps（车机 maxFPS=30）` | 出现，帧率 = 车机上限 | 若 `maxFPS` 是 60，说明这台车不是 30fps 档，帧率会自动跟到 60，无需改代码 |
| `DISPLAY: 车机 W×H（/info 通告）→ 流 …@30fps` | 车机分辨率是宽屏（≈1972×520 或更宽） | 若是「手机横屏兜底」，说明 `/info` 没取到，先查 AirPlay SETUP |
| 发出 `0x4300` 后 60~125ms 内收到 `0x4301`（含热点 SSID/密码/端口） | 收到 | 完全没有 `0x4301` → 先改选「别克 E5（手机拨号）」再试一轮；两轮都不通，把日志发我，按 `0x1D01` 身份重新定规则 |
| 触摸 | 点哪中哪 | 明显偏大/偏移 → 就是 §4 第 1 条，需要补 HID 逻辑上限换算 |
| 画面 | 满屏、比例正确 | 拉伸或裁切 → 「显示」缩放改 90% 再试 |

**拿到日志之后要做的两件事**：

1. 把 `0x1D01` 的 `name/model/manufacturer` 补进 `B233Identity.MODEL_MARKERS`，让这台车能被
   「自动识别」认出来；
2. 按实测决定要不要给这个档位改名（例如按真实车型叫「别克 GL8 大连屏」）。帧率「车机报了就跟随」
   已经是全局规则，不需要再推广；需要验证的是**奥迪那类车机报的 maxFPS 是否真是 60**——
   若它们其实报 30，说明这条规则会改变既有车机的行为，得单独复核。
