# 进程被系统冻结：如何一眼认出来，以及解冻后怎么自己爬起来

> 2026-10-30 立项。对应实现：`service/FreezeWatch.kt`、`CarPlayService`（心跳）、
> `SessionController.onProcessResumed`（恢复）、`util/LogThrottle.kt`（降噪）。

## 1. 症状长什么样

用户看到的是「画面突然定住，一两分钟后车机把会话撤了」。日志上看更像灵异事件：

```
[22:14:45.726] CARLIFE: 媒体进度 150574594ms
        ……133 秒，一行都没有……
[22:16:59.875] MEDIA: 通知监听器未被系统绑定
[22:16:59.880] AIRPLAY: 控制通道读线程结束
[22:16:59.881] EVENT/VIDEO: Connection reset / Broken pipe
[22:16:59.906] LINK closed: bt socket closed
[22:16:59.963] NSD: 服务消失 CarPlay
```

以前只能靠三个旁证去猜：日志整段空白、解冻瞬间 `实测帧率 397.4fps（5s 内 1988 帧）`、
0.5 秒内吐出上百条「媒体进度」。现在不用猜了——保活服务会直接写一行：

```
PROC: 进程被系统冻结 133 秒（心跳中断 134s）——冻结期间不发帧、不回 keepAlive，车机多半已按超时撤掉会话
PROC: 解冻 133s 自检——CarLife:7240=在监听，车机 AirPlay=不可达（多半已被车机撤掉会话），推流=已断
PROC: 重建会话 第 1/4 次（退避 3000ms · 端点 GeXu-Audi_5GHz）
PROC: ✓ 会话已自动恢复（第 1 次尝试）
```

## 2. 为什么这样判

HyperOS / MagicOS 冻结进程时**不杀进程、不报错、不回调**，所有线程一起挂起。
所以任何「应用内定时器」都停摆，唯一还会走的时钟是 `SystemClock.elapsedRealtime()`
（单调时钟，不受用户改系统时间影响，但冻结期间照常走）。

保活服务（前台服务，见 `CarPlayService`）每秒喂一次心跳给 `FreezeWatch`：

| 相邻心跳间隔 | 判定                          |
| ---------- | --------------------------- |
| ≈1000ms    | 正常                          |
| 1000~4000ms | 主线程跑重活（shell 上限 4s 等），不报 |
| ≥4000ms    | 冻结，`冻结时长 = 间隔 - 1000ms`    |

阈值取 3 秒而不是 1 秒：主线程偶尔迟到是常态，报成冻结等于把日志又糊掉。

**放在前台服务而不是会话线程**，是因为要测的正是「整个进程有没有被挂起」——
主线程的 Handler 和会话线程会一起停，解冻后谁先跑都能看到同一个跳变，主线程最稳。

## 3. 解冻后做什么

冻结结束时车机那边的账已经算完：keepAlive 超时 → 关 AirPlay 控制通道 → 撤
`_airplay._tcp` → 断蓝牙 iAP2，一条不留。**等它自己回来是等不到的**，因为车机
认为这台手机已经走了。所以由我们主动重建：

1. **先等 1.5 秒**：解冻瞬间积压的帧/回调正在涌出，先让推流线程把这口气喘完；
2. **复核**：`isStreaming()` 为真 → 只记一行「画面仍在，无需重建」，收工；
3. **自检**（写进日志便于定性）：
   - `CarLife:7240` 是否还在监听（引擎可能被一起冻掉或已退出）；
   - 车机 AirPlay 端口（端点记录的 `airPlayPort`，缺省 7000）是否可达；
4. **按退避重建**：3s → 6s → 12s → 24s，最多 4 轮
   （车机撤会话后要先关旧会话再重开端口，紧贴着连只会被 `Connection refused` 打回）；
   每轮前 `restartBluetoothForRecovery()` 拉起蓝牙组件、强释放可能僵住的
   `sessionStarting`，然后调 `onCarPlayEndpoint(lastGoodEndpoint, "解冻后自动恢复 #n")`
   完整重走「绑 WiFi → AirPlay 配对 → SETUP → RECORD → 推流」；
5. 每轮给 8 秒观察窗，`isStreaming()` 变真即判定恢复成功。

重建靠 `lastGoodEndpoint`（最后一次拿到完整热点信息的端点）。车机不会因为
「手机刚从冻结里出来」再补发一遍 0x4301，没有这份快照就无从重建。

## 4. 三条不能破的边界

1. **用户断开后不许自己爬起来**：判据是 `sessionWanted`（「启动连接」置 true、
   「断开」置 false），**不是** `connectCancelled`——链路一断 `onSenderLinkClosed()`
   就会把后者置 true，用它等于永不恢复。
2. **短冻结不惊动会话**：< `FreezeWatch.RECOVER_MIN_FROZEN_MS`(10s) 只落日志。
   3~10 秒的抖动多半只是主线程被占住，会话没受伤，重建反而多拆一次链。
3. **一次只允许一条恢复线程**（`freezeRecovery` 互斥）：冻结常常是「抖几下」，
   不互斥会叠出好几轮并行重建，互相把对方刚建好的会话拆掉。

## 5. 日志降噪（同批改动）

解冻时最刺眼的是「积压日志一次吐几百行」，所以这两类低频诊断信息加了限流
（`util/LogThrottle.kt`）：

| 日志                                   | 限流    | 原因                     |
| ------------------------------------ | ----- | ---------------------- |
| `CARLIFE: 媒体进度 xxxms`                | 10 秒  | 每秒一条，解冻时几百条同时涌出       |
| `CARLIFE: 收到媒体信息（xxB）但解析为空`          | 5 秒   | 每次媒体变化一条，对排查无帮助       |
| `MEDIA: 通知监听器未被系统绑定——已请求重绑`            | 5 分钟  | 动作仍每 10 秒做（重绑有意义），话不重复说 |

## 6. 排查关键字

| 关键字                                     | 含义                          |
| --------------------------------------- | --------------------------- |
| `PROC: 进程被系统冻结`                         | 确认被冻过，秒数就是冻结时长              |
| `PROC: 解冻 Ns 自检`                        | 冻结后的源状态（CarLife / 车机 AirPlay / 推流） |
| `PROC: 重建会话 第 n/4 次`                    | 正在按退避恢复                     |
| `PROC: ✓ 会话已自动恢复`                       | 恢复成功                        |
| `PROC: 自动恢复未成功`                         | 四轮都没起来，需要用户手动重连             |
| `PROC: 解冻后用户已断开——不自动恢复`               | 用户终态优先，符合预期                 |

## 7. 已知局限

- **只覆盖「进程还活着」的冻结**。被系统直接杀进程（LMK）走的是
  `CarApproachReceiver` + 静态接收器的「靠近车机自动拉起」路径，不是这里。
- 冻结期间**车机侧已经判死**，恢复必然是一次完整重连（3~10 秒黑屏），
  做不到无缝。
- 若冻结时用户已经拔掉车机/走远，恢复会白跑四轮（约 45 秒 + 观察窗），
  最后落一行「自动恢复未成功」。要彻底避免得配合 `CarIdleGuard` 的远离判定，
  目前只在「蓝牙已断 + 无画面 + 界面不可见」时收摊，不动这条路径。
