# 连不上时的自救：入网互斥、失败重试、邀请响应、半握手定性

> 1.2.11（主线）/ 1.2.13-switchpool（切换连接池分支）起生效。
>
> 这一版**不改善「正常车机能连多快」**，只解决「连不上之后没有人再试」。
> 起因是 2026-11-02 的 21 分钟现场日志（`CarPToCarL-log-20261102-181247.txt`）：
> 18:01:17 建链失败后到 18:12:47 整整 11 分钟零动作，而车机在这期间发了 **5 次**
> ctrl 邀请（17:57:39 / 18:01:43 / 18:03:44 / 18:08:40 / 18:10:04），一次都没应。

## 一、四处改动，各治一种症状

| 改动 | 治的症状 | 日志特征（改之前） |
| --- | --- | --- |
| 同 SSID 入网互斥 + 5s 去重 | 两条路径抢同一热点，互相 `release()` | 同一毫秒两行「以应用专属网络加入」；入网花 28s；断网时**没有任何**「已断开」日志 |
| 失败按 3s/10s/30s 退避重试 | 失败即收工，用户只能自己再点 | `STAGE: 本轮小结` 之后就再没有一行 |
| ctrl 邀请即时响应 | 车机在喊「来连」，我们不理 | `CTRL: ✓ 车机 ctrl 邀请（第 N 次…）` 后面什么都没有 |
| 半握手快速定性 | SETUP 200 但会话根本起不来，却仍然兜底硬推 | `✓ SETUP 完成 … display=2404x1200@60（车机未通告·手机兜底）` |

## 二、入网互斥为什么是非做不可的

`WifiCarPlayConnector.joinCarPlayNetwork` 的第一行是 `release()`：

```kotlin
release()   // unregisterNetworkCallback + bindProcessToNetwork(null)
```

而车机热点凭据有两条来源，会在同一瞬间各触发一次入网：

- `0x5703`（Iap2Wireless）→ `autoJoinCarWifi`
- `0x4301`（CarPlayStartSession）→ 端点交接的 `wifi-join-on-endpoint`

后发的那次 `release()` 会把先发的**就地注销**，连锁三件事：

1. 先发的永远等不到 `onAvailable` —— 白等满 15s（日志里那行「超时（15s）」是弹窗
   路径接手的假象，实际只等了 4.1 秒）；
2. `onNetworkLost` 随回调一起被注销 —— **被动断开自动重绑整条链路失效**，
   1.2.10 刚加的功能在这一轮等于不存在；
3. 用户被迫面对系统确认框，整轮从点连接到真连上花掉 28.4 秒。

现在的语义（`net/WifiJoinGate`，纯逻辑、有单测）：

- 同一 SSID 已有请求在跑 → 后来者**等它的结果**，自己不发；
- 同一 SSID 刚失败过且还在 5 秒内 → 跳过（`Skip`）；
- 用户点「重试」= `force`，只跳过第二项，**不跳过第一项**（那才是会互相 release 的情形）。

## 三、重试的节奏与边界

```
失败 → 3s → 失败 → 10s → 失败 → 30s → 停止
```

- 起点是「本轮未建立会话」且没有晚到 0x4301 可补投（有晚到端点时优先走那条）；
- 用户断开、已出画面、正在连 —— 一律不排；
- 三次用完还在失败 = 车机侧真坏了，日志明确写「请重启车机侧 CarPlay」；
- 令牌（generation）机制保证「邀请/用户操作打断退避」：挂在 `sleep` 里的旧线程
  醒来发现令牌变了就安静退出，不会叠出两轮并行交接（两轮同时配对必然互相
  `retireSession`）。

## 四、半握手：什么时候该放弃这一轮

判定条件（两条同时成立）：

1. `/info` 没给任何 displays（`setup.displayFromCar == false`）；
2. 事件通道连不上（`connectEventChannel` 返回 false）——**前提是接收端确实下发了
   `eventPort`**：压根没下发时那是「没试过」而不是「连不上」，当成证据会误判一台
   本来能用的车（这类固件正是画布兜底要照顾的对象）。

两条同时成立就是车机侧 CarPlay 服务「只答应了前半段」：SETUP 回 200，随后 7~8ms
就把 RTSP 连接 FIN 掉，事件口 `ECONNREFUSED`，屏幕流 SETUP 也过不去。这时按手机
屏幕尺寸兜一个画布硬推没有意义——屏上不会出现画面、触摸也没通路，只会把
「连不上」演成「连上了但黑屏」。

**只缺一条时不判失败**，只打警告：历史上确实有接收端不实现 `/info`（画布兜底是
为它们留的），一刀切成失败会把能用的车判死。

## 五、拿到日志怎么读

| 看到这行 | 含义 | 下一步 |
| --- | --- | --- |
| `WIFI: "X" 已有一次入网请求在跑——等它的结果` | 互斥生效（以前这里是两行并发加入） | 正常，不用管 |
| `WIFI: "X" Ns 前刚加入失败——5s 去重窗口内不重复请求` | 两条路径都失败，短时间内不再重试 | 5 秒后再看 |
| `RETRY: … 3s 后自动重试（第 1/3 次）` | 开始退避重试 | 看后面有没有出画面 |
| `RETRY: 已连续失败 3 轮，停止自动重试` | 车机侧需人工干预 | 车机上把 CarPlay 关掉再打开 |
| `CTRL: 车机邀请到达…立即发起一轮连接` | 邀请触发（空闲态） | 正常 |
| `AIRPLAY: ⚠ 车机侧 CarPlay 服务半握手` | SETUP 200 但信息口/事件口都不通 | 重启车机侧 CarPlay |
| `AIRPLAY: 主屏流 SETUP 失败——本轮不会有画面` | 会话级 SETUP 被拒 | 反复出现 → 重启车机 |

## 六、已知仍未解决的

- **WiFi 抖动后 CarPlay 会话不会自愈**：1.2.10/1.2.12 只做「把网络拉回来」，
  会话重建仍要等对端拆链或用户重连。要不要做自动重建，取决于实车抖动频率。
- **通话声音不上车机**：车机 telephony 档不含 AAC-LC/PCM 立体声位，协议层上限。
- **会话 40~80 秒被对端关闭**：需抓断链前原始字节才能定性（见
  `docs/audio-channel-watchdog.md` 的抓包口子）。

## 七、自查修补（1.2.11 之后，版本号未变）

这一轮只动「已经写下的逻辑里的漏洞」，不加新功能：

| 修补 | 原来的问题 | 后果 |
| --- | --- | --- |
| `0x4301` 也记 `lastCarWifi` | 只在 `0x5703` 里记完整凭据；BMW iD9 等**不发 0x5703** 的车型永远没有凭据 | 这些车被动断开后走「没凭据，只能提示」——1.2.10 的自动重绑对它们等于不存在；现在日志会写「本轮没有热点凭据（0x5703/0x4301 都未到）」 |
| 退避令牌与「占用排队位」同锁读取 | 令牌是出了锁才读的，中间若被用户点击/邀请 +1，这一次退避会把**新一轮**的令牌当成自己的 | 醒来判「没过期」→ 再起一轮 → 两轮并行交接（必然互相 `retireSession`） |
| 半握手判定要求「确实有 eventPort」 | 接收端不下发 `eventPort` 时 `connectEventChannel` 返回 false（但它其实没试过） | 少见的无事件口固件会被误判成「车机服务异常、请重启车机」而放弃本轮；现在退回画布兜底 |
| `WifiJoinGate.finish` 只记录「仍是当前那一发」的结果 | 换过 SSID 后旧 ticket 才结束时，会把**另一条热点**的失败写进去重状态；`await` 被中断时还吞掉了中断位 | 新热点刚失败过就被误判（反向污染）；旧热点自己的失败反而没被记住；等待方后续的阻塞调用会静默失效 |
| `VideoSender.configSent` / `passthrough` 加 `@Volatile` | 帧线程/重连线程写，保活线程读，普通字段无可见性保证 | 极端时序下空闲重发全被丢（画面静止几十秒后车机拆链），或重连后漏发 config（一帧都过不去） |
| `AacLcEncoder` 输入缓冲长度与排队长度一致 | `put` 被 capacity 截断，`queueInputBuffer` 仍按原始 size 记账；输入槽拿不到时静默丢帧 | 个别 ROM 抛 `IllegalArgumentException`；丢帧无计数，日志里只表现为「声音卡了一下」 |
| `CarPlayCtrlAdvertiser.start` 失败时关端口 | 异常路径既不关 `ServerSocket` 也不复位 `registered` | 每失败一次漏一个监听端口 |
| `WifiLinkWatchdog.eventCount` 每轮启动清零 | 计数跨轮累计，「本轮收到 N 次抖动」实际是历史总和 | 收尾日志会报上一轮的抖动次数，读日志的人按错误次数判断链路质量 |
| `WifiLinkWatchdog` 起点兜底校验 `TRANSPORT_WIFI` | WiFi 掉线后 `activeNetwork` 切到蜂窝，被当成「当前 WiFi 接口」写进 `wifi=` 项 | 日志里出现 `wifi=[rmnet_data0/10.x]`，看起来像「WiFi 接口变成了蜂窝」——其实那是 `default` 项 |
| `AacLcEncoder` 的 `encode`/`stop` 互斥 | 没有锁：收尾路径 `stop()` 与采集/注入线程的 `encode()` 并发，直接抛 `Invalid to call during stop(); only valid in executing state` | 会话收尾瞬间必现异常日志，未编码的音频帧还会碰已 release 的 codec |
| `AudioSender.sendSyncOnce` 识别 ICMP 端口不可达就地补发 | 车机 `controlPort` 没监听时每包都被拒，连接式 UDP 还是延后一拍上报 → 恒定「失败 1 次、成功 1 次」交替 | 锚点密度只有设计值一半，日志每秒刷两行；现在同一套接字立刻补发一次，锚点仍每秒一包（只提示一次） |
